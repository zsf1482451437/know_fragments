核心结论：当前 LCP 瓶颈不在服务端响应，也不在最终渲染，而在首屏图片资源链路。
优化重点： 让首屏图更早被发现、更小地下载、更快地展示。

### 问题1: 首屏 LCP 图被懒加载了
这里虽然有 `fetchpriority="high"`，但图片 class 里同时出现了 `lazyloaded`，并且存在 `data-src`。这说明首屏图可能仍然经过了懒加载链路。`fetchpriority="high"` 只能提升已经被浏览器发现的资源优先级，不能解决“资源发现太晚”的问题。

## 优化方案
- 首屏 LCP 图不要懒加载（建议首屏第一张图直接输出真实 src）
- 给首屏 LCP 图增加 preload（建议在 <head> 里预加载第一张图）
- 控制图片尺寸，避免移动端下载 3840 宽大图
- 压缩图片格式和质量
- 减少轮播脚本对首屏首帧的阻塞

### 1. 首屏 LCP 图不要懒加载

首屏第一张轮播图应直接输出真实 `src`，避免依赖 JS 把 `data-src` 替换成 `src`。

{% if forloop.first %}
  loading="eager"
  fetchpriority="high"
{% else %}
  loading="lazy"
{% endif %}
```

### 2. 给首屏 LCP 图增加 preload

在 `<head>` 中提前声明首屏图，让浏览器在解析 HTML 早期就开始下载。

```html
<link
  rel="preload"
  as="image"
  href="https://cdn.shopify.com/..."
  fetchpriority="high"
>
```

如果图片存在多端尺寸，优先使用 `imagesrcset` 和 `imagesizes`，避免 preload 了一张桌面端超大图却在移动端使用。

### 3. 控制图片尺寸，避免移动端下载 3840 宽大图

当前 LCP 图标注为 `3840 x 1400`，适合作为高清素材源，但不应该让所有设备都下载原图。Shopify 场景下可以通过 CDN 输出不同宽度。

```liquid
{{ section.settings.image | image_url: width: 1800 }}
```

推荐配合 `srcset`：

```html
<img
  src="...width=1600"
  srcset="...width=800 800w, ...width=1200 1200w, ...width=1800 1800w"
  sizes="100vw"
  loading="eager"
  fetchpriority="high"
  decoding="async"
  alt=""
>
```

### 4. 压缩图片格式和质量

优先使用 Shopify CDN 支持的现代图片格式与合理质量参数：

- 桌面端首屏图控制在业务可接受清晰度下的最小尺寸。
- 移动端使用单独裁剪图，避免下载桌面宽图再裁切展示。
- 优先使用 WebP/AVIF。
- 避免透明 PNG、超高质量 JPG 直接作为首屏 Hero 图。

### 5. 减少轮播脚本对首屏首帧的阻塞

首屏第一帧应该在 HTML 解析阶段即可被浏览器发现和加载。轮播初始化、切换动画、非首屏 slide 的懒加载可以后置。

排查重点：

- 首屏图是否依赖 JS 初始化后才插入 `src`。
- 是否先加载轮播库，再决定展示哪张图。
- 是否用 CSS background-image 承载首屏图，导致 preload scanner 不容易提前发现。
- 是否因为第三方脚本、主题脚本阻塞了首屏图片加载。

## 面试表达

这次 LCP breakdown 里，TTFB 只有 210ms，Element Render Delay 也只有 50ms，说明瓶颈不在服务端响应和浏览器最终渲染。真正的问题集中在图片资源链路：Resource Load Delay 达到 1.64s，说明首屏 Banner 图被浏览器发现得太晚，可能被 lazyload 或轮播初始化逻辑延迟；Resource Load Duration 也有 1.28s，说明图片体积偏大。

我的优化思路是先让首屏第一张图从懒加载链路中剥离出来，直接输出真实 `src`，配合 `loading="eager"`、`fetchpriority="high"` 和 `<link rel="preload">` 提前发现资源；同时通过 Shopify CDN 输出多尺寸图片和 WebP/AVIF，避免移动端下载 3840 宽大图。其他非首屏轮播图继续懒加载，这样既优化首屏 LCP，也不牺牲后续页面资源加载效率。

## 如果瓶颈是 TTFB 或 Element Render Delay

当前数据里的 `TTFB` 为 `210ms`、`Element Render Delay` 为 `50ms`，两者都不是主要瓶颈。但如果某次测试中这两个指标明显升高，可以按下面的方向排查。

### 1. TTFB 较高

`TTFB（Time to First Byte）` 是从浏览器发起请求，到收到服务器第一字节响应之间的时间，通常包含网络连接、请求排队、服务端处理和响应传输准备。

#### 常见原因

- 源站距离用户较远，DNS、TCP 或 TLS 建连耗时较高。
- CDN 未命中，动态回源或缓存配置不合理。
- 服务端生成 HTML 较慢，例如模板渲染、接口聚合、数据库查询耗时。
- Shopify 主题注入过多应用代码，导致服务端页面处理或响应体生成变慢。
- 第三方代理、WAF、网关或重定向链路增加了等待时间。
- 页面发生多次重定向，例如 HTTP 到 HTTPS、旧域名到新域名、语言或地区跳转。

#### 解决方案

- 使用 CDN 缓存可缓存的 HTML、静态资源和边缘响应，减少跨地域回源。
- 检查 DNS、HTTPS、重定向和 CDN 命中情况，减少不必要的跳转。
- 对服务端模板、接口聚合和数据库查询做耗时拆分，定位真正的等待环节。
- 减少首屏请求前必须执行的服务端逻辑和第三方应用注入。
- 对动态数据和非首屏数据延迟请求，不要阻塞初始 HTML 返回。
- 通过 `Server-Timing`、APM、CDN 日志和浏览器 Network Timing 区分 DNS、连接、排队与服务端处理耗时。

#### 面试表达

如果 TTFB 偏高，我会先在 Network Timing 中拆分 DNS、连接建立、请求排队和 Waiting for server response，判断是网络、CDN 未命中还是服务端处理慢。确认根因后，再通过 CDN 缓存、减少重定向、优化模板和接口聚合、延迟非首屏数据请求等方式降低首字节等待，而不是直接把问题归因于前端资源。

### 2. Element Render Delay 较高

`Element Render Delay` 是 LCP 资源已经完成加载后，到浏览器真正把 LCP 元素绘制出来之间的时间。如果图片下载不慢但这个阶段很长，通常说明浏览器主线程或渲染条件被阻塞。

#### 常见原因

- 主线程正在执行大量 JavaScript，存在长任务或复杂计算。
- 首屏轮播初始化、布局计算、动画或事件绑定阻塞了绘制。
- LCP 元素被 CSS 隐藏，例如 `display: none`、`opacity: 0`、`visibility: hidden`，等待脚本添加展示 class。
- CSSOM 尚未完成，关键样式或字体加载阻塞元素绘制。
- 首屏 DOM 过于复杂，样式计算、布局或重排成本较高。
- 图片加载完成后还要经过 JS 解码、裁剪、Canvas 绘制或组件状态更新。
- 第三方脚本抢占主线程，导致浏览器无法及时执行绘制任务。

#### 解决方案

- 使用 Performance 面板定位 LCP 前后的 Long Task，拆分或延后非关键 JavaScript。
- 将轮播初始化、动画、埋点和第三方 SDK 放到首屏绘制之后。
- 首屏第一帧不要依赖 JS 才从隐藏状态切换为可见状态。
- 提取关键 CSS，减少阻塞渲染的样式体积，避免复杂选择器和首屏大范围重排。
- 给图片设置明确的 `width` / `height` 或 `aspect-ratio`，减少布局抖动。
- 减少首屏 DOM 层级，避免在 LCP 元素上叠加复杂滤镜、遮罩和同步动画。
- 对非关键组件使用懒加载、代码分割和按需初始化，释放主线程。

#### 面试表达

如果 Element Render Delay 偏高，我会先确认资源是否已经下载完成，再用 Performance 面板查看 LCP 前是否存在 Long Task、布局重排或样式阻塞。优化重点会放在减少首屏同步 JavaScript、让首屏元素默认可绘制、延后轮播和第三方脚本初始化、降低首屏 DOM 与样式计算成本，确保资源到达后能尽快完成实际绘制。

## 问题: 首屏轮播图尺寸偏大
- 首屏和轮播图都在用 3840x1400 大图。
- 多张轮播图都被 Lighthouse 识别为“比实际展示需要更大”。
- 部分图片是 fetchpriority="auto" ，只有当前 LCP 图是 fetchpriority="high" 。
- Logo PNG 也被提示可以进一步压缩，说明不只是 Banner 图，站点静态图片整体还有压缩空间。
- 这类问题会影响图片下载耗时，从而影响 FCP、LCP 和用户感知加载速度。

- 用 Shopify CDN 输出响应式尺寸
- 首屏图和非首屏图分策略
- 移动端单独出图
- 压缩 Logo 和小图
- 控制轮播图数量

首屏第一张图：
```

```
其他轮播图：

```

```
### 3. 移动端单独出图
移动端不要复用桌面横幅大图。最好单独准备移动端裁剪图，比如 750x900 、 1080x1200 ，避免下载桌面图后只显示中间一部分。

### 4. 压缩 Logo 和小图
ogo 这种 25.9 KiB 的 PNG 如果没有透明复杂需求，可以尝试：
- WebP
- SVG
- 压缩 PNG
- 降低无意义的图片尺寸

### 5. 控制轮播图数量
- 首屏轮播图数量控制在 3-5 张
- 非首屏轮播图数量控制在 1-2 张

## 解决方案
- 可控资源，如主题js、css、图片等（长缓存+文件hash）
- 三方脚本，如 Analytics、Marketing、Social Media 等（评估是否需要、延迟加载非首屏、放到用户交互后加载、defer/async、自托管）

如果可控的静态资源，比如主题 JS、CSS、图片：

```
Cache-Control: public, max-age=31536000, 
immutable
```
前提是文件名带 hash，例如：

```
app.8f3a1c.js
theme.a91d.css
```
这样资源内容变了，文件名也变，浏览器不会用旧缓存。

如果是 Shopify/CDN 图片资源：

- 优先使用 Shopify CDN 自动生成的静态资源 URL；
- 图片、字体、构建产物尽量走 CDN；
- 不频繁变更的资源使用长缓存；
- 变更时通过文件名、版本号或 query 参数更新缓存。
如果是第三方脚本，比如这里的：
```text
goaffpro/loader.js
cloudflare-static/email-decode.min.js
```

说明页面配置了超过 4 个 preconnect 。 preconnect 会提前建立 DNS、TCP、TLS 连接，本身也有成本。如果对很多域名都提前连接，但这些域名并不一定会马上请求资源，就会浪费连接资源，甚至和真正的关键请求竞争网络资源。

不要对所有第三方域名都加 preconnect ，尤其是：

- 只在用户交互后才加载的脚本；
- 非首屏统计工具；
- 偶尔才请求的营销插件；
- 实际没有资源请求的域名。

判断标准是：这个域名是否会在页面早期请求关键 CSS、字体、LCP 图片或核心接口。如果不是，就不应该提前连接。

## 优化方向

- 减少 HTML 中的同步脚本和阻塞 CSS；
- 非首屏第三方脚本使用 async 、 defer 或延迟到交互后加载；
- 首屏 LCP 图片直接从 HTML 可发现，必要时使用 preload；
- 不要让 JS 执行后才请求首屏图片、字体或关键接口；
- 合并或减少关键 CSS/JS 的串行依赖；
- 检查 Shopify 应用是否向主题注入了多层脚本；
- 对首屏不需要的 Klaviyo、广告、客服、热力图脚本延迟加载；
- 只对真正关键的域名保留 preconnect ；
- 使用 Chrome DevTools Network 的 Initiator 和 waterfall 查看每条请求是谁触发的。
