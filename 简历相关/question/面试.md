## CSS
### BFC 块级格式化上下文怎么理解
答：
可以理解成页面里的一个独立布局区域。
这个区域内部的元素按自己的规则参与布局，内部布局不会影响外部，外部浮动、margin 等也不容易干扰它。
常见触发 BFC 的方式：
overflow: hidden;
display: flow-root;
display: inline-block;
position: absolute;
position: fixed;
float: left;
最常见的实际用途有三个：
1. 清除浮动
父元素里面全是浮动元素时，高度可能塌陷：
```css
.parent {
  overflow: hidden;
}
```
让父元素形成 BFC 后，就能包住内部浮动元素。
2. 避免 margin 重叠
普通块级元素上下 margin 可能合并。创建 BFC 后，可以隔离 margin，避免父子或相邻元素 margin 合并。
3. 避免文字环绕浮动元素
左边有浮动元素，右侧内容可能围绕它排列。让右侧内容形成 BFC 后，就能独立占据剩余空间，不和浮动元素重叠。

### position relative 是相对于什么定位
答：
相对于元素自己的位置。

### 在一个需要左右布局场景下，左边元素填充高度要和右边元素一样，但是左右元素内容都是不固定的，用flex布局怎么实现

答：
用 flex 做左右等高布局时，核心是让外层容器 `display: flex`，并保持交叉轴默认的 `align-items: stretch`。这样左右两个 flex item 会自动被拉伸到同一行里最高那个元素的高度。

```css
.layout {
  display: flex;
  align-items: stretch;
}

.left {
  width: 240px;
  background: #f5f5f5;
}

.right {
  flex: 1;
}
```

```html
<div class="layout">
  <aside class="left">左侧内容</aside>
  <main class="right">右侧内容很多，高度不固定</main>
</div>
```

这里不需要手动写固定高度，因为 flex 容器在一行布局里会先根据左右内容算出这一行的高度，再把两个子项在交叉轴上拉伸到同样高度。左边内容少、右边内容多时，左边也会被撑到和右边一样高；反过来也一样。

要注意不要给容器写 `align-items: flex-start`，否则左右元素就不会自动等高。如果左边内部还有一层需要铺满高度，可以让左边自己也变成 flex：

```css
.left {
  width: 240px;
  display: flex;
  flex-direction: column;
}

.left-content {
  flex: 1;
}
```

面试里可以总结成一句：左右内容都不固定时，不要靠 JS 算高度，也不要写死高度；用 flex 容器默认的 `align-items: stretch` 实现同一行子项等高，内部再用 `flex: 1` 填充剩余高度。

## JS
### 原型链

答：
JavaScript 里每个对象内部都有一个 `[[Prototype]]`，通常可以通过 `__proto__` 间接访问。对象在读取某个属性时，会先在自己身上找；如果找不到，就沿着它的原型对象继续往上找，一直找到 `null` 为止，这条查找路径就是原型链。

比如数组可以直接调用 `map`、`filter`，不是因为数组实例自己有这些方法，而是因为会沿着原型链找到 `Array.prototype`。原型链的意义主要有两个：一是实现属性和方法复用，二是支撑 JS 的继承模型。

结合工程经验，实例对象放自己的数据，共享方法放到原型上，这样比给每个实例都拷一份方法更节省内存。

q11: 那像普通函数，怎么查找它的原型方法呢？

答：
普通函数本身也是对象，所以它也有原型链。要区分两个概念：

第一，函数作为“构造函数”时，有一个 `prototype` 属性，这个属性是给实例对象用的。比如 `Foo.prototype.say = ...`，以后 `new Foo()` 出来的实例就能沿着原型链找到 `say`。

第二，函数自己作为一个对象，也能调用 `call`、`apply`、`bind` 这些方法。这些方法不是函数自己定义的，而是沿着原型链找到 `Function.prototype` 上的。

函数对象先看自己身上有没有，没有就沿着 `__proto__` 往上找，先到 `Function.prototype`，再到 `Object.prototype`，最后到 `null`。

### 事件循环

答：
宏任务是“外部事件进入 JS 主线程的入口”

执行一个宏任务 / task 
  -> 调用栈清空（同步代码，函数调用都执行完）
  -> 执行 microtask checkpoint
  -> 清空所有微任务
  -> 如果微任务里又产生新的微任务，也继续执行
  -> 浏览器有机会渲染
  -> 执行下一个宏任务

常见宏任务有 script、setTimeout、I/O、UI 事件；常见微任务有 Promise.then、queueMicrotask、MutationObserver。

这个机制和性能优化也有关系。如果一个任务里塞了很多同步计算，或者不断产生微任务，就会长时间占用主线程，导致渲染和用户输入被延后，页面看起来就会卡。

```js
console.log('1')

setTimeout(() => {
  console.log('2')
}, 0)

Promise.resolve().then(() => {
  console.log('3')
})

console.log('4')
1432
```

## 浏览器
### 浏览器输入 URL 到页面渲染完成发生了什么

答：
我会按“网络请求、资源解析、渲染流水线、运行时交互”四个阶段讲。

第一步是 URL 解析和网络连接。浏览器解析 URL，检查缓存，如果没有命中缓存，会做 DNS 解析，拿到 IP 后建立 TCP 连接；如果是 HTTPS，还会进行 TLS 握手。

第二步是发送 HTTP 请求。服务端返回 HTML，浏览器根据状态码、响应头、缓存策略、压缩方式等处理响应。

第三步是解析 HTML。浏览器边下载边解析 HTML，构建 DOM 树；遇到 CSS 会下载并解析成 CSSOM；DOM 和 CSSOM 合并生成 Render Tree。

第四步是执行 JS。遇到普通 script 时，浏览器会暂停 HTML 解析，下载并执行 JS，因为 JS 可能会修改 DOM 或样式。

第五步是布局和绘制。浏览器根据 Render Tree 计算每个元素的位置和尺寸，也就是 layout；然后进行 paint，把颜色、文字、图片、边框等绘制出来；最后通过合成线程把不同图层 compositing 到屏幕上。

如果是 React 页面，HTML 加载后还会下载 JS bundle，执行 React 初始化、创建虚拟 DOM、绑定事件、发起接口请求，最终把数据渲染到页面上。

### DOM/CSS 解析过程中遇到 JS 阻塞该怎么优化

答：
主要有几类手段。

第一是给脚本加 `defer` 或 `async`。`defer` 会让 JS 下载和 HTML 解析并行，等 DOM 解析完成后按顺序执行；适合依赖 DOM 和有执行顺序要求的业务脚本。`async` 是下载完成就执行，不保证顺序，适合统计、埋点这类独立脚本。

第二是把 script 放到 body 底部，至少让主要 HTML 先解析出来。

第三是拆包和按需加载。比如 React 项目里用路由懒加载、组件懒加载，把首屏不需要的 JS 延后下载和执行。

第四是减少主线程长任务。大计算可以拆分、放到 Web Worker，或者用 requestIdleCallback、setTimeout 分片，避免一次 JS 执行太久阻塞解析和渲染。

第五是优化 CSS。因为 CSS 会影响渲染树和布局，关键 CSS 可以内联，非关键 CSS 延后加载，减少 CSS 阻塞渲染的时间。

首屏一打开就必须正确展示的样式：
- 顶部导航：高度、背景色、布局、Logo 尺寸
- 首屏 Banner / Hero：容器高度、图片比例、标题字号、CTA 按钮样式
- 首屏商品卡片：价格、按钮、主图比例、基础栅格布局
- 骨架屏：占位块尺寸、背景色、圆角
- 防 CLS 样式：图片容器宽高比、 aspect-ratio 、固定高度

首屏看不到、或者用户交互后才出现的样式：
- Footer 样式
- 评论区样式
- 推荐商品区样式
- 弹窗 / 营销浮层样式
- 客服组件样式
- 非首屏活动楼层样式
- 复杂动画、轮播切换特效样式
- 后台编辑器、富文本、图表等重组件样式

在 Next.js 里，常见做法不是手写全部 inline，而是：
- 首屏组件样式跟随页面主包加载
- 非首屏组件用 next/dynamic 拆出去
- 组件自己的 CSS 跟着异步 chunk 加载


### 为什么 JS 解析会阻塞 DOM 树解析

答：
因为 JavaScript 有修改 DOM 和 CSSOM 的能力，浏览器为了保证执行结果符合代码顺序，遇到普通同步 script 时必须暂停 DOM 解析，先下载并执行 JS。

举个例子，如果 HTML 解析到一半时遇到：

```html
<script>
  document.write('<div>new content</div>')
  document.querySelector('.title').remove()
</script>
```

这段 JS 可能插入新节点、删除已有节点、读取样式、修改 class。如果浏览器一边继续解析后面的 HTML，一边执行这段 JS，就可能导致 DOM 顺序和脚本预期不一致。

另外，如果 JS 里读取样式，比如 `getComputedStyle` 或 `offsetHeight`，它还可能依赖已经解析好的 CSSOM。所以浏览器通常还要等待前面的 CSS 加载和解析完成，避免 JS 读到错误的样式结果。

所以总结就是：JS 阻塞 DOM，是因为它能改 DOM；CSS 可能阻塞 JS，是因为 JS 可能读样式；这三者之间有顺序依赖。




### localStorage、sessionStorage、cookie 有什么区别
答：

| 对比项 | localStorage | sessionStorage | cookie |
| --- | --- | --- | --- |
| 生命周期 | 手动清除前一直存在 | 当前标签页会话结束后清除 | 可设置过期时间 |
| 容量 | 通常 5MB 左右 | 通常 5MB 左右 | 通常 4KB 左右 |
| 是否随请求发送 | 不会 | 不会 | 会自动随同域请求发送 |
| 作用域 | 同源共享 | 同源 + 同标签页 | 可通过 Domain/Path 控制 |
| JS 是否可读 | 可读写 | 可读写 | 默认可读写，`HttpOnly` 后 JS 不可读 |
| 常见用途 | 主题配置、长期缓存、非敏感偏好 | 表单草稿、单页临时状态 | 登录态、服务端鉴权、灰度标识 |

## React
### useEffect 第一个参数有什么要求

答：
`useEffect` 的第一个参数必须是一个函数，也就是 effect callback。React 会在组件渲染提交到页面之后执行这个函数。

这个函数有几个要求：

第一，不能直接写成 `async` 函数。因为 async 函数返回的是 Promise，而 `useEffect` 期望返回的是 `undefined` 或一个清理函数。如果要发异步请求，应该在内部定义 async 函数再调用。

```tsx
useEffect(() => {
  async function loadData() {
    const data = await fetchData()
    setData(data)
  }

  loadData()
}, [])
```

第二，可以返回一个 cleanup 函数，用来清理定时器、事件监听、订阅、AbortController 等副作用。

```tsx
useEffect(() => {
  const controller = new AbortController()

  fetch(url, { signal: controller.signal })

  return () => controller.abort()
}, [url])
```

第三，effect 里用到的外部变量，原则上要放到依赖数组里，避免闭包拿到旧值。比如用到了 `url`、`userId`，依赖数组就应该包含它们。

一句话总结：第一个参数必须是同步函数，可以返回清理函数，不能直接返回 Promise；副作用里用到的响应式变量，要通过依赖数组保证执行时机正确。

从 React 原理上看，`useEffect` 不是在 render 阶段执行的，而是在组件完成渲染并提交到 DOM 之后，由 React 在 commit 阶段统一调度的 Passive Effect。React 调用 effect 回调时，需要立刻拿到一个确定的返回值，用来判断后续是否要注册 cleanup。如果回调直接写成 `async`，返回值一定是 `Promise`，React 无法把这个 Promise 当作清理函数执行，也无法等待它再决定 cleanup，所以规范要求 effect 回调本身必须是同步函数。

cleanup 的本质是 React 在下一次 effect 重新执行前，或者组件卸载时，用来清理上一次副作用的同步函数。比如上一次 effect 里注册了事件监听、定时器、订阅、网络请求控制器，React 需要在依赖变化时先执行旧 cleanup，再执行新的 effect，避免重复订阅、内存泄漏和竞态更新。如果返回的是 Promise，React 不知道什么时候清理完成，也不能保证 commit 阶段副作用队列的执行顺序。

依赖数组对应的是 React 判断“这次提交后，这个 effect 是否需要重新执行”的依据。函数组件每次 render 都会形成一份新的闭包快照，effect 里访问的 `props`、`state`、函数和变量，本质上都来自某一次 render。如果依赖数组漏掉了这些响应式变量，React 可能会复用旧 effect，导致 effect 里的闭包仍然拿着旧值，这就是常说的 stale closure。依赖写完整，就是告诉 React：这些值变化后，旧副作用需要清理，新副作用需要基于最新闭包重新建立。

面试可以这样说：`useEffect` 的设计是把副作用从 render 阶段拆到 commit 之后执行，所以 render 必须保持纯净，effect 回调也要同步返回 cleanup 约定；异步逻辑可以放在 effect 内部执行，但不能让 effect 本身返回 Promise。依赖数组则是 React 基于闭包和 Object.is 比较来判断副作用是否需要重新同步的机制，写错依赖就容易出现旧值、重复订阅或请求竞态。

如果要把 React 的渲染和重渲染也画成链路图，可以记成：

```mermaid
flowchart TD
    A[首次入口 createRoot/render]
    B[进入 render 阶段]
    C[执行函数组件/生成新的 UI 描述]
    D[Fiber 协调与 Diff]
    E[进入 commit 阶段]
    F[更新真实 DOM]
    G[浏览器绘制]
    H[执行 effect]

    I[setState / props / context 变化]
    J[React 创建 update]
    K[按优先级调度更新]
    L[重新执行组件函数]
    M[生成新的 UI 描述]
    N[和旧 Fiber 树做 Diff]
    O[提交最小 DOM 变更]
    P[cleanup 旧 effect]
    Q[执行新 effect]

    A --> B --> C --> D --> E --> F --> G --> H
    I --> J --> K --> L --> M --> N --> O --> P --> Q
```


### React 更新机制
### Diff 算法流程

答：
React 的 diff 可以理解成一次从旧 Fiber 树到新 Fiber 树的对比过程，目标是找出最小的更新集合，最后在 commit 阶段把变化同步到真实 UI。

整体流程我会分三层讲：

第一层是节点类型对比。如果新旧节点类型不同，比如从 `div` 变成 `span`，或者从一个组件变成另一个组件，React 通常会认为这棵子树不能复用，直接卸载旧节点，创建新节点。

第二层是同类型节点复用。如果节点类型相同，React 会复用已有 Fiber 和对应 DOM，只更新变化的 props，比如 className、style、事件回调、文本内容等。

第三层是子节点列表 diff。React 会重点看 `key`。如果有稳定 key，就用 key 判断哪些节点可以复用、哪些需要新增、删除或移动；如果没有 key，就只能按位置比较，列表插入、删除、重排时容易造成不必要的更新。

在 Fiber 架构下，diff 发生在 render/reconcile 阶段，这个阶段可以被中断。React 会通过 `child / sibling / return` 指针遍历 Fiber 树，对每个节点执行 `beginWork` 和 `completeWork`，并给需要更新的 Fiber 标记副作用。最后 commit 阶段是同步不可中断的，把插入、更新、删除这些变化真正提交到 DOM 或原生视图。

面试里我会总结成一句：React diff 的核心假设是不同类型节点不复用，同类型节点尽量复用，列表用 key 提高复用准确性；Fiber 让这个比较过程可以拆分和调度，最终把变化集中到 commit 阶段提交。

### Fiber 架构

答：
React 引入 Fiber，核心是为了解决老架构同步递归渲染不可中断的问题。

早期 React 更新组件树时，一旦开始 diff 和渲染，就会一直执行到整棵树处理完，中间不能暂停。如果组件树很大，就会长时间占用主线程，用户点击、输入、动画这些高优先级交互会被阻塞。

Fiber 可以理解成 React 内部一种新的节点结构和调度模型。它把原来一次性递归处理的大任务拆成一个个可调度的工作单元。这样 React 就能在渲染过程中暂停、恢复、丢弃或者重做任务，并且给不同更新分优先级。

所以 Fiber 带来的价值主要是三点：可中断渲染、优先级调度、为并发能力比如 `startTransition`、`Suspense` 打基础。

q31: 那fiber架构里面reconciler是怎么遍历那棵树的？

答：
Reconciler 遍历 Fiber 树时整体是深度优先。先通过 child 指针向下执行 beginWork ；如果当前节点没有 child，就执行 completeWork 回溯；回溯时优先找 sibling ，有兄弟节点就处理兄弟，没有兄弟节点就通过 return 回到父节点。su

![alt text](assets/image.png)

```bash
A beginWork
  -> 有 child，进入 B

B beginWork
  -> 有 child，进入 D

D beginWork
  -> 没有 child，开始 completeWork
  -> D 有 sibling，进入 E

E beginWork
  -> 没有 child，completeWork
  -> E 没有 sibling，return 回 B
  -> B completeWork
  -> B 有 sibling，进入 C

C beginWork
  -> 没有 child，completeWork
  -> C 没有 sibling，return 回 A
  -> A completeWork
```

## 工程化
### 工程化做过哪些

答：
我做过的工程化主要有三类：规范治理、构建提效、流程沉淀。

第一类是规范治理。我搭过 `ESLint + Prettier + Commitlint + Husky` 这一套，把代码风格、提交规范和提交前检查前置，减少低价值 review 和低级问题进仓库。

具体做法是把“靠人提醒”的规则前置到工具链里。比如 ESLint 负责约束未使用变量、Hook 依赖、React 组件写法；Prettier 负责格式统一；Commitlint 约束提交信息必须符合 `feat/fix/chore` 这类规范；Husky 在 `pre-commit` 阶段跑 lint-staged，只检查本次改动文件，避免全量检查太慢。

一个典型链路是：

```text
开发提交代码
  -> Husky 触发 pre-commit
  -> lint-staged 只拿 staged 文件
  -> ESLint 修复/拦截明显问题
  -> Prettier 统一格式
  -> Commitlint 校验 commit message
  -> 通过后才允许进入仓库
```

这样做的收益是 review 时不用再反复纠结缩进、分号、命名这类低价值问题，团队可以把精力放到业务逻辑、性能和可维护性上。

第二类是构建和依赖治理。我做过项目从 npm 切到 pnpm，规范依赖安装和构建流程，把安装时间从 10 秒降到 5 秒以内；在商城项目里也做过依赖治理、包体积分析和构建优化，支撑性能提升。更具体地说，我会把构建提效拆成三层：开发启动提效、生产构建提效、交付验证提效。

具体案例是：原来项目用 npm，每次安装依赖都会在当前项目下重复拷贝大量包，CI 或新同事初始化时等待时间比较长。我切到 pnpm 后，会同步做三件事：第一，锁定 `packageManager`，保证团队都用同一个 pnpm 版本；第二，提交 `pnpm-lock.yaml`，保证 CI 和本地依赖版本一致；第三，把安装命令、构建命令、Node 版本写进 README 或脚本里，避免每个人本地环境不一致。

### 案例 1：Next.js 跨境商城首屏包体积治理

在跨境商城项目里，我会先用 `@next/bundle-analyzer` 看哪些依赖进入了首页 initial bundle。常见问题是营销弹窗、评论组件、推荐商品、客服入口、富文本编辑器、图表库这类非首屏模块被直接 import 到首页，导致首屏 JS 下载、解析和执行都变重。

我的处理链路是：

```text
bundle analyzer 定位首屏大模块
  -> 判断是否首屏必须
  -> 非首屏组件 next/dynamic 拆包
  -> 重库按需引入或替换轻量实现
  -> 验证 initial JS、LCP、Long Task 是否下降
```

比如评论区、客服、营销弹窗不影响用户第一眼看到商品信息，我会改成动态加载或按页面加载：

```tsx
const ReviewSection = dynamic(() => import("./ReviewSection"), {
  ssr: false,
  loading: () => <ReviewSkeleton />,
});
```

如果发现引入整个工具库，比如一次性引入完整 `lodash`、图标库或图表库，我会改成按需引入，或者替换成更轻的实现。最终目标不是为了“少几个 KB”而优化，而是减少首屏 JS 下载、解析和执行成本，支撑 LCP、TTI、INP 这些体验指标。

### 案例 2：AI Agent 电商系统的 Vite 构建和验证链路

本地开发 vite dev 快速启动

### 案例 3：Node 应用的 Docker 构建部署

代码提交

同时我会配合 Shell 脚本处理镜像打包、版本命名和产物压缩，减少重复操作。这个收益是新环境部署更稳定，线上回滚也更清楚，不依赖某台机器上“刚好装了什么依赖”。

### 更体现能力的构建提效点

构建提效不只是“换 Vite”或“换 pnpm”，更重要的是把构建过程变成可度量、可约束、可复用、可诊断的工程体系。我会重点做这几类：

1. **构建产物分析和包体积预算**：不是只临时看一次 bundle analyzer，而是给首页 initial JS、路由 chunk、vendor chunk 建预算线。
2. **依赖准入和重依赖替换**：新增依赖要判断是否进入首屏、是否支持 Tree Shaking、是否有轻量替代。
3. **CI 构建缓存**：缓存 pnpm store、Next `.next/cache`、Vite/Turbo 缓存，避免流水线每次从零开始。
4. **Docker layer cache**：先复制 `package.json` 和 lockfile 安装依赖，再复制业务代码，让业务代码变更不影响依赖层缓存。
5. **增量构建和任务分层**：本地只做快速反馈，CI 做完整校验，发布前做 smoke test，避免所有检查都压在开发阶段。
6. **构建失败可诊断化**：锁定 Node/pnpm 版本，环境变量缺失提前失败，构建日志按 lint、typecheck、test、build 分段。

可操作步骤：

```text
第一步：建立基线
  -> 记录当前安装耗时、dev 启动耗时、build 耗时、initial JS 体积
  -> 用 bundle analyzer 输出首页和核心路由包体积

第二步：治理依赖
  -> 找出进入首屏包的重依赖
  -> 判断是否首屏必须
  -> 非首屏组件 next/dynamic
  -> lodash / 图标库 / 图表库改按需引入或轻量替换

第三步：建立预算
  -> 首页 initial JS 不超过约定阈值
  -> 单个异步 chunk 超过阈值需要说明原因
  -> 新增大型依赖需要在 MR 里说明用途和替代方案

第四步：优化 CI
  -> 缓存 pnpm store
  -> 缓存 Next.js .next/cache 或构建工具缓存
  -> lint、typecheck、test、build 分阶段执行
  -> 只在必要阶段跑 e2e / smoke test

第五步：优化 Docker 构建
  -> 先复制 package.json / lockfile
  -> 安装依赖形成独立 layer
  -> 再复制业务代码
  -> 构建镜像并打版本 tag
  -> 支持按 tag 回滚

第六步：持续验证
  -> 每次优化后对比 build 时间、包体积、LCP、Long Task
  -> 把结果沉淀到文档或检查清单
```

面试表达：

> 构建提效我不只关注工具替换，而是从依赖安装、开发反馈、生产构建、CI 缓存、产物治理和失败诊断几个环节做闭环。比如跨境商城里用 bundle analyzer 做首屏包预算和依赖治理；个人全栈项目里用 Vite + Vitest + TypeScript 建立 `verify` 链路；Node 应用里用 Docker layer cache 和版本化镜像保证部署一致性。最终目标不是单纯缩短几秒构建时间，而是让团队开发反馈更快、构建结果更稳定、线上产物更可控。

pnpm 快主要是因为它用了全局内容寻址存储。相同版本的依赖只会在全局 store 里保存一份，不会像 npm 那样在每个项目里重复拷贝完整依赖。项目里的 node_modules 更多是通过硬链接和符号链接指向全局 store，所以二次安装、多个项目复用依赖时会明显更快，也更省磁盘空间。

另外 pnpm 的依赖结构更严格，只有 package.json 里声明过的依赖才能直接访问，这能减少幽灵依赖问题。配合 lockfile 和 workspace，在团队项目或 monorepo 里可以让依赖安装、版本一致性和构建流程更稳定。

幽灵依赖最大的问题是依赖关系不显式，项目稳定性变差（本地能跑，换环境、升级依赖、CI 构建或线上部署就突然报错。）。比如我代码里直接 import dayjs ，但 package.json 没声明 dayjs，只是因为某个 UI 库间接依赖了它，本地 node_modules 扁平化后刚好能访问。后面 UI 库升级、CI 重装依赖或者切到 pnpm 后，dayjs 不再暴露到当前项目，构建就会报 Cannot find module。pnpm 的严格依赖隔离能提前暴露这类问题，逼着我们把直接使用的依赖写清楚。

第三类是流程沉淀。比如在应用项目里，我引入 Docker 做镜像化部署，隔离宿主机环境差异；再配合 Shell 脚本自动化处理镜像打包、版本命名和文件压缩，减少重复部署工作。后续在团队协作中，我还沉淀过一套活动页交付检查清单，以及一套 AI 辅助研发工作流，覆盖需求拆解、代码草拟、问题排查、测试补充和文档生成。

## 性能优化
### 整体思路

答：
我之前做性能优化不是先上来改代码，而是先把问题拆成“资源体积、资源发现、资源下载、主线程渲染、缓存复用、第三方脚本”几层。

定位工具上，我会先用 `Lighthouse` 看 LCP、TBT、CLS 和具体诊断项，用 `Chrome Performance` 看主线程是否被 JS 长任务阻塞，用 `Network waterfall` 看首屏资源加载顺序和 Initiator，再用 `@next/bundle-analyzer` 分析首页 bundle，确认哪些模块和依赖进入了首屏。

在跨境商城项目里，最后定位到的问题主要集中在四块：首屏 JS 太大、首屏 Banner 图片链路重、第三方脚本过多、缓存和网络依赖链不够干净。最终通过拆包、依赖治理、图片优化、字体优化、第三方脚本延后和缓存策略，把关键 JS 从 3MB 降到 600KB，首页 LCP 从 4s 优化到 2s 以内。

### Initial JS 从 3MB 到 600KB 怎么做

优化的是首页首屏关键 JS，也就是 initial JS，不是整个项目总代码量。Next.js 本身有页面级拆包能力，我做的主要是在这个基础上继续做组件级拆分和依赖治理。

**组件级动态加载**：我先用 bundle analyzer 看首页 initial bundle 里有哪些模块实际不是首屏必须，比如营销弹窗、推荐商品、评论区、客服入口、部分活动组件。然后用 `next/dynamic` 把这些模块拆到异步 chunk 里，首屏只保留导航、Banner、核心商品信息和 CTA。这样不是把代码“消灭”，而是避免非首屏代码阻塞首屏加载和执行。

**依赖治理和 Tree Shaking**：除了拆 chunk，我也会看哪些依赖本身体积大或被重复打包。比如工具函数、日期处理、图标、富交互组件等，能按需引入就按需引入；只用少量能力的重库会替换成轻量实现；重复依赖会统一版本。导入方式上尽量使用 ESM，避免整包引入，保证 Tree Shaking 能生效。

这里要注意，dynamic import 本身更多是降低首屏 initial JS，不一定降低总 JS；真正减少总体积的是依赖替换、按需引入、重复依赖治理和 Tree Shaking。

### LCP 从 4s 到 2s 怎么做

我会先看 Lighthouse 的 LCP breakdown，把 LCP 拆成四段：

```text
TTFB
Resource Load Delay
Resource Load Duration
Element Render Delay
```

比如一次首页首屏 Banner 的分析里，TTFB 只有 210ms，Element Render Delay 只有 50ms，但 Resource Load Delay 达到 2s多，Resource Load Duration 也有 1.28s。这个结论说明瓶颈不在服务端响应，也不在最终渲染，而是在首屏图片资源链路：图片被浏览器发现得太晚，同时图片下载体积偏大。

**资源发现优化**：如果 LCP 图虽然有 `fetchpriority="high"`，但同时有 `data-src`、`lazyloaded` 这类懒加载痕迹，就说明它可能要等 JS 或轮播初始化后才真正被发现。`fetchpriority` 只能提高已经被发现的资源优先级，不能解决“发现太晚”的问题。所以首屏第一张 Banner 要直接输出真实 `src`，不要依赖 JS 把 `data-src` 替换成 `src`；必要时在 `<head>` 里用 preload 提前声明。

**Next.js 图片落地**：如果是 Next 项目，我会把普通 `img` 替换成 `next/image`，配置合适的 `width/height` 或 `fill`，保证容器尺寸稳定，减少 CLS；同时配置 `sizes`，让移动端、平板、桌面端加载不同尺寸的图，避免移动端下载桌面大图。首屏 LCP 图不做懒加载，使用 `priority` 或新版本里的 `preload` / `fetchPriority="high"`；非首屏图片继续懒加载。

```tsx
import Image from 'next/image'

export function HeroBanner() {
  return (
    <Image
      src="https://cdn.shopify.com/..."
      alt="Hero banner"
      width={1920}
      height={700}
      sizes="100vw"
      priority
      fetchPriority="high"
      quality={80}
    />
  )
}
```

如果图片来自 Shopify CDN，也可以结合 Shopify 的图片宽度参数或自定义 loader，让不同视口拿到不同尺寸，而不是所有设备都下载 3840 宽的大图。

**图片交付优化**：Lighthouse 如果提示 “image file is larger than it needs to be”，说明实际下载尺寸大于展示尺寸。我的处理是用 CDN 输出多尺寸图片，配合 `srcset/sizes` 或 `next/image` 的响应式能力；移动端单独出裁剪图；Banner、Logo、小图分别压缩；优先使用 WebP/AVIF。首屏图和非首屏图要分策略：第一张图 eager + high priority，其他轮播图 lazy + auto priority。

**字体落地方式**：字体优化上，我会用 `next/font` 做本地托管和 preload，减少外部字体请求带来的 DNS/TLS 开销。同时控制字体字重和字体数量，比如只保留页面实际用到的字重，避免一次加载多个无用 font-weight。这样能减少字体阻塞和字体切换导致的布局抖动。

**JS 阻塞治理**：如果 Performance 里看到 LCP 延迟不是图片下载，而是 Element Render Delay 高，说明资源已经到了，但浏览器没及时绘制。常见原因是主线程 Long Task、轮播初始化、动画、复杂布局计算、CSS/字体阻塞，或者 LCP 元素先被 `display:none` / `opacity:0` 隐藏，等 JS 加 class 后才展示。这个时候要延后轮播初始化、埋点和第三方 SDK，减少首屏同步 JS，让 LCP 元素默认可绘制。

### TTFB 高怎么处理

TTFB 是从浏览器发起请求到收到第一字节之间的时间。如果 TTFB 高，我会先在 Network Timing 中拆 DNS、TCP/TLS、请求排队和 Waiting for server response，判断是网络连接、CDN 未命中、重定向，还是服务端渲染或接口聚合慢。

在 Next.js 里，稳定内容我会优先用 SSG/ISR，让页面可以被 CDN 缓存；商品详情、活动页、SEO 落地页这类内容如果不是强实时，可以用 `revalidate` 做增量更新。接口数据也要避免串行等待，能并行就用 `Promise.all`，非首屏数据不要阻塞初始 HTML。

```tsx
export const revalidate = 300

const [banner, products] = await Promise.all([
  getBanner(),
  getProducts(),
])
```

同时要避免无意中使用 `cookies()`、`headers()` 或每次请求都 `no-store`，导致页面从静态渲染退化成动态渲染，把服务端耗时直接传导到首屏。

### 第三方脚本治理

跨境商城会有很多第三方脚本，比如 GA/GTM、广告像素、客服、评论插件、营销弹窗、转化追踪。我的处理不是简单全部删掉，而是先按“业务必要性 + 页面路径 + 加载时机”分层。

- 首屏必须的保留，比如核心统计或必要转化追踪，用 `afterInteractive`。
- 非首屏必须的延后，比如客服、评论、弹窗、推荐脚本，用 `lazyOnload`。
- 只在特定页面需要的，就按页面加载，不全站注入。

比如 GA4 和 Meta Pixel 属于核心转化追踪，首屏后要尽快可用，我会用 `next/script` 的 `afterInteractive`，保证 React 页面可交互之后再加载，避免阻塞 HTML 解析和首屏渲染：

```tsx
<Script
  id="ga4"
  src="https://www.googletagmanager.com/gtag/js?id=G-XXXX"
  strategy="afterInteractive"
/>
```

像客服、评论、营销弹窗、推荐商品这类组件，不影响用户第一眼看到商品和价格，我会放到 `lazyOnload`，等浏览器空闲后再加载：

```tsx
<Script
  id="customer-chat"
  src="https://chat.example.com/sdk.js"
  strategy="lazyOnload"
/>
```

如果 Lighthouse 提示第三方脚本有 Legacy JavaScript，比如 Klaviyo 脚本里包含 `Array.prototype.flat`、`Object.fromEntries`、`Promise.allSettled` 这类 polyfill，我不会直接改第三方产物。因为它来自供应商，改了可能影响功能和升级。我会先评估它是否必须首屏加载，再通过延迟加载、只在需要页面加载，或者确认供应商是否提供 modern bundle 来处理。这个收益通常低于 LCP 图片和首屏 JS，优先级要排在后面。

落地时我会配合 Chrome Performance 和 Network 看两类数据：一是首屏请求数有没有减少，二是 Main Thread 上第三方脚本造成的 Long Task 有没有下降。比如把客服和评论从首屏同步加载改成 `lazyOnload` 后，首页初始请求会更干净，主线程空闲时间更早出现，LCP 和 INP 都会更稳定。

### 缓存和构建怎么配合

Next 构建后的 JS/CSS 文件名带 hash，可以配合 CDN 做长缓存，比如：

```http
Cache-Control: public, max-age=31536000, immutable
```

可以把 **Next + CDN 长缓存** 理解成这条链路：

```text
代码构建
  -> Next 生成带 hash 的静态资源
  -> 上传/部署到服务器或 CDN 源站
  -> CDN 根据 Cache-Control 缓存资源
  -> 用户访问页面
  -> HTML 引用具体 hash 文件
  -> 浏览器/CDN 命中缓存
  -> 下次发版 hash 变化，自动请求新资源
```

关键点是：HTML 入口不做长时间强缓存，保证发版后能拿到最新资源引用；JS/CSS/hash 图片可以长缓存，因为内容变化后 URL 会变。比如第一次发版引用 `app-a8f3d2.js`，下一次发版变成 `app-b7c9e1.js`，浏览器会把它当成新资源重新请求，所以不会因为长缓存拿旧代码。

如果 Lighthouse 提示缓存 TTL 太短，要先区分资源是否可控。自有主题 JS、CSS、图片可以通过 hash + 长缓存处理；Shopify/CDN 资源优先用平台生成的版本化 URL；Klaviyo、GoAffPro、Cloudflare 这类第三方脚本的缓存头通常不能直接改，更现实的方式是评估必要性和加载时机，而不是为了分数强行自托管。

### Network dependency tree 怎么看

Lighthouse 的 Network dependency tree 主要看关键资源链有没有过长，比如初始 HTML 后才触发某个第三方脚本，第三方脚本再请求自己的 chunk，形成串行依赖。报告里如果出现 “Maximum critical path latency 7s+”，我会结合 Network waterfall 和 Initiator 看每个资源是谁触发的，减少阻塞 CSS、同步 JS 和不必要的第三方脚本。

如果报告提示 `preconnect` 超过 4 个，也不是越多越好。`preconnect` 会提前建立 DNS、TCP、TLS 连接，本身也消耗连接资源。我只会给首屏早期真正关键的来源加，比如 Shopify CDN、核心字体源；客服、营销插件、热力图、评论这类非首屏或交互后才用的域名，不应该全部预连接。

### 面试收口

所以我做性能优化的核心思路是：先用 Lighthouse、Performance、Network 和 bundle analyzer 定位瓶颈，再按优先级处理。首屏慢不一定都是 JS 问题，也可能是 LCP 图片发现太晚、图片太大、TTFB 高、主线程渲染被阻塞、第三方脚本抢占资源，或者缓存和网络依赖链不合理。Next.js 项目里我会结合 `next/image`、`next/font`、`next/script`、`next/dynamic`、SSG/ISR、CDN 缓存这些能力，把优化落到页面和构建链路里，最后用 LCP、Network transfer size、Long Task 和业务指标验证结果。

### 性能优化里面，一般关注哪些指标，这些指标受哪些因素影响

答：
我一般会分成三类指标看：用户体验指标、网络资源指标、运行时指标。

第一类是用户体验指标，也就是 Core Web Vitals：

1. `LCP`，最大内容绘制，反映首屏核心内容什么时候出来。它主要受 TTFB、首屏图片大小、图片发现时机、CSS/JS 阻塞、字体加载、服务端渲染速度影响。
2. `INP`，交互响应，反映用户点击、输入后页面响应快不快。它主要受主线程长任务、JS 包体积、复杂计算、React 重渲染、第三方脚本抢占主线程影响。
3. `CLS`，布局偏移，反映页面加载过程中稳不稳定。它主要受图片/广告/iframe 没有预留尺寸、字体替换、异步插入内容、骨架屏高度不稳定影响。

第二类是网络资源指标，比如 `TTFB`、`FCP`、资源体积、请求数量、缓存命中率、关键请求链路。这里影响因素通常是服务端响应、CDN、接口耗时、图片压缩、JS/CSS 体积、HTTP 缓存策略、第三方资源数量。如果是电商页面，我会特别看首屏大图、商品图、字体、营销插件脚本，因为这些很容易拉高 LCP 和总传输体积。

第三类是运行时指标，比如 Long Task、主线程阻塞时间、JS 执行时间、内存占用、React 组件渲染次数。这类问题一般来自 bundle 过大、一次性加载太多逻辑、列表渲染没有虚拟化、状态设计导致大范围重渲染、复杂动画或滚动监听没有节流。

我实际排查时不会只看一个 Lighthouse 分数，而是会结合 Performance、Network、Coverage 和 bundle analyzer。比如 LCP 慢，我会先判断是服务端慢、资源发现晚，还是图片太大；INP 差，就看是否有长任务和不必要重渲染；CLS 高，就查没有固定宽高的图片、广告位和异步内容。最后会用优化前后的 LCP、INP、资源体积、接口耗时和业务转化数据来验证效果。

### 对于瀑布流的布局，CLS 如何优化

答：
瀑布流最容易产生 CLS 的原因是图片高度不确定。图片加载前卡片高度是 0 或预估不准，图片加载后高度突然撑开，下面的内容就会被挤下去。所以优化核心是：在真实资源加载完成前，就把每个卡片应该占用的空间提前稳定下来。

我一般会从几层处理：

1. **图片必须有宽高或比例信息**。接口最好返回图片的原始 `width/height`，前端根据容器宽度计算展示高度，或者用 `aspect-ratio` 提前预留空间。这样图片没加载出来时，布局高度也已经确定。
2. **使用占位图或骨架屏**。卡片图片区域先渲染一个固定比例的占位块，图片加载完成后只替换内容，不改变容器尺寸。
3. **避免图片加载后再重新排版**。如果瀑布流算法依赖图片真实高度，最好在布局前就拿到尺寸数据；不要等图片 `onload` 后再把卡片插入或重新计算整列，否则会造成明显跳动。
4. **新增内容只向下追加**。分页加载或无限滚动时，新增卡片应该追加到已有内容下面，不要因为新图片加载完成导致前面已展示的卡片重新分配列。
5. **广告、推荐位、异步模块也要预留高度**。瀑布流里不只是图片会造成 CLS，异步插入的营销卡片、广告位、推荐卡片如果没有固定高度，也会把下面内容顶开。

如果是 React/Next.js 项目，我会优先用 `next/image` 或统一的图片组件，要求传入 `width/height` 或固定比例；列表数据里也会保留图片尺寸字段。面试里可以总结成一句：瀑布流优化 CLS 的关键不是图片加载得多快，而是图片加载前布局就要稳定，核心手段是尺寸数据前置、比例占位、骨架屏和避免已渲染内容重新排版。

### 包体积优化，有哪些方面

答：
包体积优化我一般不会一上来就盲目删代码，而是先用工具定位，再按收益处理。常用的是 `webpack-bundle-analyzer`、`@next/bundle-analyzer`、Vite 的 `rollup-plugin-visualizer`，先看哪些依赖进入了首屏包、哪些 chunk 过大、有没有重复依赖。

具体可以从几方面做：

1. **路由和组件级拆包**。首屏不需要的模块不要进 initial bundle，比如评论区、客服、营销弹窗、图表、富文本编辑器，可以用 `dynamic import`、`React.lazy` 或 `next/dynamic` 延后加载。
2. **依赖按需引入**。避免整包引入，比如 `lodash`、图标库、组件库、日期库。能用 ESM 按需引入就按需引入，只用少量功能时可以换轻量实现。
3. **Tree Shaking 生效**。优先使用 ESM 包，避免 CommonJS 或有副作用的导入方式；库本身要正确声明 `sideEffects`，业务代码也不要用会破坏静态分析的写法。
4. **重复依赖治理**。检查 lockfile 和 bundle，避免同一个库多个版本同时被打进产物，比如多个版本的 `lodash`、`dayjs`、组件库依赖。
5. **移除无用代码和资源**。删除未使用页面、组件、样式、polyfill、国际化语言包、图标、图片；大型静态资源不要直接打进 JS 包。
6. **第三方脚本分层加载**。统计、客服、评论、营销插件这类第三方脚本按页面和时机加载，不要全部放到全局 layout 或入口文件里。
7. **构建时分包配置**。Webpack 里可以通过 `optimization.splitChunks` 把公共依赖、业务公共模块拆出来，比如把 React、组件库、工具库放到 vendor chunk，把多个页面复用的业务组件放到 common chunk。Vite/Rollup 里可以通过 `build.rollupOptions.output.manualChunks` 手动拆分大依赖，比如图表库、编辑器、地图 SDK。分包不是越碎越好，要结合 HTTP/2、缓存命中和首屏请求数控制 chunk 数量，避免拆出太多小文件反而增加调度成本。
8. **构建压缩和缓存**。生产环境开启 minify、压缩、代码分割，静态资源带 hash 后配合 CDN 长缓存；这不能减少源码体积，但能减少传输体积和重复下载成本。

在 Next.js 项目里，我会重点区分 `initial JS` 和总 JS。Next 本身会做页面级拆包和框架运行时代码拆分，业务侧更多是通过 `next/dynamic`、路由边界、依赖治理来控制哪些代码进入首屏。除非 analyzer 明确看到某个大依赖被多个入口重复打包，否则我不会随便改 Webpack 分包策略，因为过度手动分包可能影响缓存、加载顺序和升级兼容性。`dynamic import` 主要是降低首屏 initial JS，让首屏更快可交互；如果想真正减少总体积，还要做依赖替换、按需引入、重复依赖治理和无用代码清理。

比如一个商城首页里同时引入了评论区、富文本详情、图表分析和客服组件，analyzer 看下来首页 initial JS 很大。这时候我不会先去手改复杂的 `splitChunks`，而是先判断哪些模块不是首屏必须的：评论区和客服改成 `next/dynamic`，图表分析只在活动页或运营后台加载，富文本库如果首页只是展示少量文案，就替换成更轻的渲染方案。这样通常先把真正不该进首页的代码移出去，收益会比手工拆 vendor chunk 更直接，也更稳。

如果 analyzer 进一步发现 `lodash`、组件库和一些公共业务组件被商品页、活动页、首页重复打进多个入口，那这时才适合补 `splitChunks`。例如 Webpack 可以这样配：

```js
optimization: {
  splitChunks: {
    chunks: 'all',
    minSize: 20000,
    cacheGroups: {
      vendors: {
        test: /[\\/]node_modules[\\/]/,
        name: 'vendors',
        priority: 10,
        reuseExistingChunk: true,
      },
      common: {
        minChunks: 2,
        name: 'common',
        priority: 5,
        reuseExistingChunk: true,
      },
    },
  },
}
```

这个配置的意思是：第三方依赖尽量归到 `vendors`，多个入口复用的业务模块归到 `common`。这样首页、商品页、活动页第一次访问后，后续页面切换就更容易命中缓存，不用每个入口都重复下载一份相同代码。不过我在面试里也会补一句：这类配置只适合“确实存在重复打包”的场景，前提还是先用 analyzer 证明问题，不然很容易把 chunk 拆得过碎。

面试里可以这样收口：包体积优化的流程是先用 analyzer 建立基线，再看首屏包里是否混入了非首屏模块和重依赖；处理手段包括拆包、懒加载、Tree Shaking、按需引入、替换重库、去重依赖、移除无用资源和第三方脚本治理；最后用 initial JS、chunk size、Network transfer size、LCP 和 Long Task 验证效果。

### 这些性能指标该怎么收集

答：
我一般会分成两类来收集：实验室指标和真实用户指标。

第一类是实验室指标，也就是开发和测试阶段主动测出来的数据。常用工具是 `Lighthouse`、Chrome DevTools 的 `Performance`、`Network`、`Coverage`、`WebPageTest`。这类工具适合定位问题，比如看 LCP 拆解、TTFB、关键请求链、Long Task、CLS 来源、资源体积和主线程阻塞。优点是环境可控、方便复现，适合优化前后对比；缺点是它模拟的是理想或固定环境，不一定等于真实用户体验。

第二类是真实用户指标，也就是 RUM。这个一般是在页面里接入 `web-vitals`，或者用监控平台收集真实用户的 `LCP`、`INP`、`CLS`、`FCP`、`TTFB`，再带上页面路由、设备类型、网络类型、地区、浏览器版本这些维度一起上报。这样才能知道线上到底是哪些用户慢、哪个页面波动大、优化有没有真实收益。

如果是 Next.js 项目，我会用 `useReportWebVitals` 或直接接 `web-vitals` 做上报，把指标发到埋点平台或监控系统。比如：

```ts
export function reportWebVitals(metric) {
  window.gtag?.('event', metric.name, {
    value: Math.round(metric.name === 'CLS' ? metric.value * 1000 : metric.value),
    metric_id: metric.id,
    metric_value: metric.value,
    metric_delta: metric.delta,
  })
}
```

除了核心 Web Vitals，我还会补一些辅助维度一起看，比如：

1. 页面 URL 和路由类型；
2. 设备型号、浏览器、系统版本；
3. 网络类型，比如 4G、Wi-Fi；
4. 国家地区、是否命中 CDN；
5. 资源体积、接口耗时、错误率。

这样排查时就不会只看到“平均值”。比如某个页面平均 LCP 还行，但 Android 低端机或弱网用户特别差，这种问题只有真实用户监控才能看出来。

面试里我一般会这样收口：性能指标收集不是只跑一次 Lighthouse，而是“实验室指标做定位，真实用户指标做验证”。开发阶段用 Lighthouse、Performance、Network 找瓶颈；上线后用 `web-vitals` 或监控平台收集 LCP、INP、CLS、TTFB，再按页面、设备、网络和地区分维度分析，最后结合业务转化看优化效果。

## SEO
### SEO 优化怎么做

答：
我做的主要是基础 SEO 和页面结构优化，场景主要在商品页、活动页和解决方案页。

我的做法一般分四层：

1. Meta 信息维护，比如 `title`、`description`、`canonical`、Open Graph，保证每个页面主题明确。
2. 语义化结构，页面会保留清晰的 `h1/h2` 层级，以及 `section/article` 这些语义化标签，让搜索引擎更容易理解内容结构。
3. 让核心内容可索引。像商品标题、卖点、规格、FAQ、活动规则这些内容，尽量在 SSR/SSG 阶段输出，而不是完全依赖客户端异步渲染。
4. 做图片和性能优化，比如补充 `alt`、控制图片尺寸、首屏图优先加载、非首屏图懒加载，避免资源过重影响抓取和首屏体验。

在实际项目里，我覆盖了 20+ 商品和活动页面的基础 SEO 配置。我的理解是 SEO 不是单纯写几个 Meta，而是 `元信息 + 结构 + 可索引内容 + 性能` 一起做。

### Meta 数据是谁写的

答：

如果是商品页、活动页、解决方案页这类前端页面，我会负责把 Meta 的生成逻辑接到页面里，包括 `title`、`description`、`canonical`、OG 等字段的渲染和校验。具体文案内容通常会和运营、产品一起对齐，确保页面主题、关键词和实际内容一致。

如果是批量页面，我不会手工一个个硬编码，而是会基于页面数据、商品信息或者活动配置去生成，保证可维护性和一致性。上线前我也会检查页面源码、分享卡片和 Lighthouse SEO 基础项，确认 Meta 生效。

所以更准确的说法是：技术接入和页面渲染逻辑是我负责，具体业务文案会和运营协作完成。

## 跨端
### React Native 和 React 有什么区别、优缺点是什么

答：
React 和 React Native 的核心思想是一致的，都是组件化、声明式 UI、状态驱动视图，也都可以用 Hooks、状态管理和 React 的组件模型。

区别主要在渲染目标不同。React Web 最终渲染的是浏览器 DOM，写的是 `div、span、button` 这些 Web 元素；React Native 最终渲染的是原生视图，写的是 `View、Text、Image、ScrollView` 这些 RN 组件，由 RN 桥接或新架构把 JS 层的描述同步到 iOS/Android 原生层。

样式也不同。Web 用 CSS、布局模型、选择器；RN 用类似 CSS 的 JS 对象，默认 Flex 布局，没有完整 CSS 选择器，也没有浏览器 DOM API。调试和性能问题也不同，Web 更关注浏览器渲染、资源加载、LCP/CLS；RN 更关注 JS 线程、UI 线程、Native 通信、列表渲染、内存和多机型兼容。

RN 的优点是跨平台复用度高，一套 React 技术栈可以同时支持 iOS 和 Android，迭代效率比纯原生高，也方便前端同学上手。像我之前在智能安防类 App 项目里，就用 RN 承接设备接入、消息提醒、实时预览、录像回放这些业务链路，很多业务逻辑可以跨双端复用。

缺点是复杂原生能力、性能敏感场景和平台差异仍然需要原生协作，比如摄像头、视频流、蓝牙、推送、权限、Native Module、不同系统版本兼容等。RN 不是完全替代原生，而是适合把业务 UI 和跨端逻辑提效，底层能力仍然要和原生配合。

面试总结就是：React 是 Web UI 框架，React Native 是用 React 模型开发原生 App 的跨平台框架；优点是跨端复用和迭代效率高，缺点是复杂原生能力和性能问题需要更强的调试与平台协作能力。

### Hooks 机制
### Hooks 为什么不能放在循环和条件判断里

答：
因为 React Hooks 是靠调用顺序来关联状态的，而不是靠变量名。

React 在函数组件每次渲染时，会按 Hooks 调用的先后顺序记录状态，比如第一个 `useState` 对应第一个状态，第二个 `useEffect` 对应第二个 effect。如果 Hooks 放在条件判断或循环里，不同渲染之间 Hooks 的调用顺序或调用次数可能变化，React 就会把状态对应错。

比如：

```tsx
function Demo({ visible }: { visible: boolean }) {
  const [name, setName] = useState('')

  if (visible) {
    const [age, setAge] = useState(0)
  }

  const [count, setCount] = useState(0)
}
```

第一次 `visible = true` 时，Hooks 顺序是：

```text
useState(name)
useState(age)
useState(count)
```

下一次 `visible = false` 时，Hooks 顺序变成：

```text
useState(name)
useState(count)
```

这样 React 原本记录在第二个位置的状态可能被错误地当成 `count`，状态就乱了。

所以 Hooks 必须放在函数组件最外层，保证每次渲染调用顺序一致。如果有条件逻辑，可以把条件放到 Hook 内部，比如在 `useEffect` 里面判断，或者把逻辑拆成自定义 Hook，但自定义 Hook 本身也要遵守同样规则。

### const 怎么实现
答：
让“变量名和内存地址/引用之间的绑定关系”不可重新指向。
```js
const a = 1
a = 2 // TypeError
```
但对象内部属性仍然可以改：
```js

obj.a = 2 // OK
obj = {}       // TypeError
```
原理：
- JS 引擎在词法环境里创建一个不可重新赋值的 binding。
- 声明时必须初始化。
- 初始化前处于 TDZ，也就是暂时性死区，不能访问。
- 后续如果执行赋值操作，引擎会检查这个 binding 的可写标记，发现不可写就抛 TypeError 。

可以类比成：
const obj = 地址 0x001
obj 这个变量名永远只能绑定到 0x001 ，但 0x001 里的对象属性可以变。
如果想让对象内容也不能改，需要：

```js
const obj = Object.freeze({ name: 'A' })

obj.name = 'B' // 严格模式下报错，非严格模式下静默失败
```
只允许初始化一次，后续不允许重新赋值 ：
```js
function createConst(initialValue) {
  let initialized = true
  let value = initialValue

  return {
    get() {
      return value
    },
    set() {
      if (initialized) {
        throw new TypeError('Assignment to constant variable.')
      }
    }
  }
}

const name = createConst('Alice')

console.log(name.get()) // Alice
name.set('Bob')         // TypeError
```

### 手写发布订阅 EventEmitter

回忆链路：

```text
事件中心
  -> 用 Map 存 eventName 和 listeners
  -> on: 注册回调
  -> emit: 找到回调列表并依次执行
  -> off: 从回调列表里删除指定函数
  -> once: 包一层 wrapper，执行后自动 off
```

核心点：
- 一个事件名可以绑定多个回调。
- `emit` 时要把参数透传给回调。
- `off` 删除的是同一个函数引用。
- `once` 本质是注册一个包装函数，执行一次后把自己移除。
- `emit` 时最好拷贝一份 listeners，避免执行过程中 `off/on` 影响当前遍历。

```js
class EventEmitter {
  constructor() {
    this.events = new Map()
  }

  on(eventName, listener) {
    if (!this.events.has(eventName)) {
      this.events.set(eventName, [])
    }

    this.events.get(eventName).push(listener)

    return this
  }

  emit(eventName, ...args) {
    const listeners = this.events.get(eventName)

    if (!listeners || listeners.length === 0) {
      return false
    }

    // 拷贝一份，避免执行回调时修改原数组影响本轮触发
    listeners.slice().forEach((listener) => {
      listener(...args)
    })

    return true
  }

  off(eventName, listener) {
    const listeners = this.events.get(eventName)

    if (!listeners) {
      return this
    }

    const nextListeners = listeners.filter((item) => {
      return item !== listener && item._origin !== listener
    })

    if (nextListeners.length === 0) {
      this.events.delete(eventName)
    } else {
      this.events.set(eventName, nextListeners)
    }

    return this
  }

  once(eventName, listener) {
    const wrapper = (...args) => {
      try {
        listener(...args)
      } finally {
        this.off(eventName, wrapper)
      }
    }

    // 记录原始函数，方便 off(eventName, listener) 也能删掉 once 包装函数
    wrapper._origin = listener

    return this.on(eventName, wrapper)
  }
}

const emitter = new EventEmitter()

function handleMessage(message) {
  console.log(message)
}

emitter.on('message', handleMessage)
emitter.emit('message', 'hello') // hello
emitter.off('message', handleMessage)

emitter.once('login', (user) => {
  console.log('login', user)
})

emitter.emit('login', 'Tom') // login Tom
emitter.emit('login', 'Tom') // 不再触发
```

面试表达：

> 发布订阅的核心是维护一个事件中心，用事件名映射回调数组。`on` 负责收集订阅，`emit` 负责按事件名触发回调，`off` 负责删除指定回调，`once` 是在原回调外面包一层，触发后自动解绑。实现时要注意回调引用一致性，以及 emit 时拷贝 listeners，避免遍历过程中数组被修改。


### 手写 Promise

回忆链路：

```text
状态机
  -> pending / fulfilled / rejected
  -> resolve: pending -> fulfilled
  -> reject: pending -> rejected
  -> then: 收集成功/失败回调
  -> 异步执行回调
  -> then 返回新 Promise
  -> 根据回调返回值决定新 Promise 状态
```

核心点：
- Promise 状态只能从 `pending` 变成 `fulfilled` 或 `rejected`，并且只能变一次。
- executor 立即执行，执行异常要进入 reject。
- then 必须返回一个新的 Promise，才能链式调用。
- 如果 then 回调返回普通值，新 Promise resolve 这个值。
- 如果 then 回调返回 Promise，新 Promise 要跟随它的状态。
- 原生 Promise 回调用微任务执行，面试手写可以用 `queueMicrotask` 模拟。

```js
const PENDING = 'pending'
const FULFILLED = 'fulfilled'
const REJECTED = 'rejected'

function isPromiseLike(value) {
  return value !== null &&
    (typeof value === 'object' || typeof value === 'function') &&
    typeof value.then === 'function'
}

function resolvePromise(promise, result, resolve, reject) {
  if (promise === result) {
    return reject(new TypeError('Chaining cycle detected for promise'))
  }

  if (isPromiseLike(result)) {
    let called = false

    try {
      result.then(
        (value) => {
          if (called) return
          called = true
          resolvePromise(promise, value, resolve, reject)
        },
        (reason) => {
          if (called) return
          called = true
          reject(reason)
        }
      )
    } catch (error) {
      if (!called) {
        reject(error)
      }
    }

    return
  }

  resolve(result)
}

class MyPromise {
  constructor(executor) {
    this.status = PENDING
    this.value = undefined
    this.reason = undefined
    this.onFulfilledCallbacks = []
    this.onRejectedCallbacks = []

    const resolve = (value) => {
      if (this.status !== PENDING) return

      if (isPromiseLike(value)) {
        value.then(resolve, reject)
        return
      }

      queueMicrotask(() => {
        if (this.status !== PENDING) return

        this.status = FULFILLED
        this.value = value
        this.onFulfilledCallbacks.forEach((callback) => callback())
      })
    }

    const reject = (reason) => {
      if (this.status !== PENDING) return

      queueMicrotask(() => {
        if (this.status !== PENDING) return

        this.status = REJECTED
        this.reason = reason
        this.onRejectedCallbacks.forEach((callback) => callback())
      })
    }

    try {
      executor(resolve, reject)
    } catch (error) {
      reject(error)
    }
  }

  then(onFulfilled, onRejected) {
    const realOnFulfilled = typeof onFulfilled === 'function'
      ? onFulfilled
      : (value) => value

    const realOnRejected = typeof onRejected === 'function'
      ? onRejected
      : (reason) => {
          throw reason
        }

    const nextPromise = new MyPromise((resolve, reject) => {
      const fulfilledTask = () => {
        queueMicrotask(() => {
          try {
            const result = realOnFulfilled(this.value)
            resolvePromise(nextPromise, result, resolve, reject)
          } catch (error) {
            reject(error)
          }
        })
      }

      const rejectedTask = () => {
        queueMicrotask(() => {
          try {
            const result = realOnRejected(this.reason)
            resolvePromise(nextPromise, result, resolve, reject)
          } catch (error) {
            reject(error)
          }
        })
      }

      if (this.status === FULFILLED) {
        fulfilledTask()
      } else if (this.status === REJECTED) {
        rejectedTask()
      } else {
        this.onFulfilledCallbacks.push(fulfilledTask)
        this.onRejectedCallbacks.push(rejectedTask)
      }
    })

    return nextPromise
  }

  catch(onRejected) {
    return this.then(undefined, onRejected)
  }

  finally(callback) {
    return this.then(
      (value) => MyPromise.resolve(callback()).then(() => value),
      (reason) => MyPromise.resolve(callback()).then(() => {
        throw reason
      })
    )
  }

  static resolve(value) {
    if (value instanceof MyPromise) {
      return value
    }

    return new MyPromise((resolve, reject) => {
      if (isPromiseLike(value)) {
        value.then(resolve, reject)
      } else {
        resolve(value)
      }
    })
  }

  static reject(reason) {
    return new MyPromise((resolve, reject) => {
      reject(reason)
    })
  }

  static all(promises) {
    return new MyPromise((resolve, reject) => {
      const result = []
      let count = 0

      if (promises.length === 0) {
        resolve(result)
        return
      }

      promises.forEach((promise, index) => {
        MyPromise.resolve(promise).then(
          (value) => {
            result[index] = value
            count += 1

            if (count === promises.length) {
              resolve(result)
            }
          },
          reject
        )
      })
    })
  }

  static race(promises) {
    return new MyPromise((resolve, reject) => {
      promises.forEach((promise) => {
        MyPromise.resolve(promise).then(resolve, reject)
      })
    })
  }
}

const p = new MyPromise((resolve) => {
  resolve(1)
})

p.then((value) => {
  console.log(value) // 1
  return value + 1
}).then((value) => {
  console.log(value) // 2
})

MyPromise.all([
  MyPromise.resolve(1),
  2,
  new MyPromise((resolve) => resolve(3))
]).then((list) => {
  console.log(list) // [1, 2, 3]
})
```

面试表达：

> 手写 Promise 先抓住状态机：`pending`、`fulfilled`、`rejected`。构造函数里立即执行 executor，`resolve/reject` 只能改变一次状态。`then` 的核心是返回一个新的 Promise；如果当前 Promise 已经完成，就异步执行回调；如果还在 pending，就先把回调存起来，等状态改变后再执行。链式调用的关键在 `resolvePromise`：回调返回普通值就 resolve，返回 Promise 就递归等待它的最终状态，同时要处理循环引用。

## 电商业务系统设计
### 支付与交易链路

### 自建站支付方式怎么对接

答：
接第三方支付平台，比如 PayPal、信用卡支付，我们系统侧主要做的是订单创建、支付单创建、跳转收银台或拉起支付组件、接收支付回调、更新订单状态。

PayPal 链路：
前端加载 PayPal JS SDK
  -> 渲染 PayPal Button
  -> 用户登录 PayPal 并授权
  -> 前端拿到 orderID / authorization
  -> 后端调用 PayPal API capture
  -> webhook 或 capture 结果确认支付成功
  -> 更新订单状态


信用卡支付链路：
后端创建 payment intent
  -> 前端用支付 SDK 加载支付组件
  -> 用户输入卡信息
  -> SDK 返回 payment method / token
  -> 前端提交给后端
  -> 后端确认支付
  -> 支付平台 webhook 通知支付结果
  -> 后端验签并更新订单

这里有几个关键点。

第一，支付状态不能以前端跳转结果为准。前端成功页只能作为用户体验，真正可信的是支付平台的服务端回调，也就是 webhook。因为用户可能关闭页面、网络中断，或者伪造前端成功跳转。

第二，回调必须做验签和幂等。支付平台回调可能重复推送，所以后端要根据支付单号、订单号和事件 ID 做幂等处理，已经处理过的回调不能重复改状态、重复扣库存或重复发货。

第三，订单状态要拆清楚。一般会有 `pending_payment`、`paid`、`failed`、`cancelled`、`refunded` 这些状态，支付前创建订单但不进入履约，只有收到可信回调确认支付成功后，才把订单改为已支付。

第四，金额要以后端为准。前端只负责展示，实际支付金额必须由后端根据商品、SKU、优惠、税费、运费重新计算，避免用户篡改请求金额。

如果是跳转收银台，前端集成成本低，但体验和可定制性弱；如果是 SDK 方式，体验更好，可以嵌入站内 checkout，但要更关注安全合规、回调验签、幂等和异常状态处理。


### 平台迁移与商品同步
### 从平台站迁到自建站会有哪些问题

答：
从 Shopify 独立站迁到自建站，最大的问题不是页面重写，而是 Shopify 原来帮你兜住的能力要不要自己承担。

第一是交易链路。商品、SKU、库存、购物车、结算、支付、订单、退款、税费、物流这些能力，在 Shopify 里是平台能力；自建站后就要自己设计数据模型、接口、事务和异常兜底。

第二是运营生态。Shopify 有很多成熟 app，比如评论、折扣、邮件营销、自定义商品、数据分析。如果自建站，这些能力要么自研，要么重新选型集成。

第三是 SEO 和流量迁移。URL 结构、301 重定向、canonical、站点地图、结构化数据都要处理，否则原来的搜索权重可能会掉。

第四是稳定性和安全。自建站要自己处理接口限流、黑名单、支付风控、库存并发、日志监控、发布回滚和数据备份。

所以我会倾向于分阶段做：第一阶段可以用 Headless Shopify，让前端自建体验，但商品、库存、订单仍复用 Shopify；第二阶段再逐步把核心业务服务拆出来，避免一次性迁移风险过大。

### 商品定制与履约
### 自定义印名印号的交互方式和订单落库原理

答：
交互上一般是在商品详情页或购物车前增加一个自定义区域，比如用户选择球衣尺码之后，可以输入姓名、号码，或者选择字体、颜色、位置。前端会做长度、敏感词、字符类型、号码范围这些基础校验，并实时预览效果。

原理上，在 Shopify 里这类自定义信息通常不会作为普通 SKU 处理，而是作为 line item properties 跟着购物车项进入 checkout。也就是说，用户加入购物车时，不只是传 variant id 和 quantity，还会把 `Name`、`Number`、`Font` 这类自定义字段作为属性一起提交。

订单创建后，这些 properties 会出现在订单的 line item 下面。后台、履约系统或者打印系统读取订单时，就能拿到对应商品的自定义信息，用于生产和发货。

所以核心链路是：

```mermaid
flowchart TD
    A[商品详情页输入自定义信息]
    B[前端校验和预览]
    C[加入购物车时写入 line item properties]
    D[Checkout 创建订单]
    E[订单 line item 携带自定义字段]
    F[后台履约/打印读取字段]

    A --> B --> C --> D --> E --> F
```

### 用户自定义图片要怎么处理

答：
自定义图片会比文字复杂，重点是上传、校验、存储和订单关联。

前端会先做基础校验，比如文件类型、大小、尺寸、比例、透明背景、分辨率是否满足印刷要求。然后把图片上传到后端或对象存储，比如 S3、OSS、Shopify Files 等，后端返回一个稳定的图片 URL 或文件 ID。

加入购物车时，不建议把图片本身塞进订单，而是把图片 URL、文件 ID、预览图 URL、印刷位置等信息写到 line item properties。订单履约时再根据这个 URL 下载原图或读取文件 ID。

同时要考虑安全和生产风险：图片需要做类型白名单、病毒扫描、鉴黄/违规内容识别、访问权限控制和过期策略。如果是印刷场景，还要保留原图和预览图，避免用户看到的效果和实际生产文件不一致。

### 自定义印名印号为什么不做成 SKU 变体

答：
主要原因是自定义信息的组合数量太大，不适合做成 SKU 变体。

SKU 适合表达有限、可库存管理的商品差异，比如颜色、尺码、版本。但印名印号是用户自由输入的，比如姓名可以有很多组合，号码也有很多组合，如果把每个姓名和号码都做成变体，会导致 SKU 爆炸，商品维护、库存管理、搜索展示和后台操作都会变得不可控。

另外，印名印号本质上不是库存维度，而是订单生产属性。用户买的还是某个球衣 SKU，只是在这件商品上附加了个性化生产信息。所以更合理的方式是：SKU 管颜色和尺码，自定义 app 管姓名、号码、图片、字体、位置等订单附加信息。

这样既不会污染商品 SKU 体系，也方便履约系统按订单行读取定制信息。

## 架构与工程设计
### 新建一个项目时怎么考虑框架选型、构建工具、依赖管理和性能优化

答：
如果新建一个项目，我不会一上来先选技术，而是先看业务形态、团队情况和交付要求。

第一是看项目类型。如果是官网、商城、内容 SEO 比较重的项目，我会优先考虑 Next.js，因为它支持 SSR/SSG、路由、图片和字体优化，对首屏和 SEO 更友好；如果是中后台、管理端、SaaS 控制台这类强交互项目，我会考虑 React + Vite，开发体验轻，构建速度快；如果是移动端跨平台 App，我会考虑 React Native。

第二是看团队技术栈。如果团队 React 经验更多，就优先 React 生态；如果团队已有 Vue 组件库和历史项目，也会尊重现有资产。技术选型不是只看框架先进，而是要看团队能不能稳定维护。

第三是构建工具。新项目一般我会优先 Vite，启动快、配置轻、生态成熟；如果是 Next 项目就沿用 Next 自身构建体系；老项目或复杂定制构建才会继续用 Webpack。构建上会提前考虑环境变量、别名、按需加载、包体积分析和生产构建校验。

第四是依赖管理。我会优先用 pnpm，安装快、磁盘占用低，也能更好地暴露幽灵依赖问题。项目初期会约定 Node 版本、包管理器版本、lockfile、依赖升级策略，避免不同同学本地环境不一致。

第五是工程规范。会接入 TypeScript、ESLint、Prettier、Commitlint、Husky，再加上统一的 `lint / typecheck / test / build` 命令，把低级问题前置到提交前和 CI 阶段。

第六是性能和质量。前期就会考虑路由拆包、组件懒加载、图片压缩、缓存策略、首屏资源控制，以及埋点、错误监控和测试覆盖。像我之前做商城项目时，也会用 bundle analyzer 先看首屏包体积，再做依赖治理和动态加载。

所以我的选型链路是：先看业务目标，再看团队能力，再定框架、构建、依赖、规范、性能和交付流程。

### 现在要做一个公司内部使用的微应用平台，各个业务部都可以在平台上发布自己的微应用，使用平台上的微应用，如果你负责这个事情的话，你怎么去完成这个需求？你觉得这个微应用平台该去做哪些关键的设计？

答：
我会先把这个需求拆成两层：一层是“平台能力”，也就是各业务部能注册、发布、下线、升级自己的微应用；另一层是“运行时能力”，也就是公司内部用户能在统一门户里稳定、安全地使用这些微应用。

整体架构可以理解成：

```text
统一门户 / 主应用
  -> 应用市场 / 应用目录
  -> 权限与组织体系
  -> 微应用运行容器
  -> 发布平台 / 版本管理
  -> 监控、日志、告警
```

第一是接入规范。每个业务部不能随便部署一个页面就接进来，要有统一的应用元信息，比如应用名称、负责人、所属部门、访问路径、图标、描述、权限范围、入口地址、版本号、健康检查地址。这样平台才能做应用目录、搜索、审核、灰度、下线和问题追责。

第二是微应用运行容器。技术上可以选 `qiankun`、Module Federation、iframe，或者自研轻量容器。我的选择会看隔离要求：如果各业务应用技术栈不同、发布频率不同，微前端方案更适合独立开发和部署；如果安全隔离要求很强，iframe 隔离更彻底，但通信和体验成本更高。主应用负责统一导航、登录态、菜单、主题和公共 SDK，子应用只负责自己的业务页面。

第三是权限和组织治理。公司内部平台一定要接 SSO 或统一登录，权限不能只靠前端菜单隐藏。平台侧要支持按组织、角色、用户、应用维度授权；后端接口也要校验权限。比如财务应用只能财务部门访问，HR 应用只能 HR 和相关审批人访问，平台管理员负责应用审核和权限配置。

第四是发布和版本管理。业务部提交微应用后，平台要支持注册、构建、部署、审核、灰度、回滚这些流程。至少要区分 dev、test、prod 多环境；每次发布要记录版本、发布人、变更说明和产物地址。出现问题时，可以快速回滚到上一个稳定版本。

第五是运行时隔离和稳定性。微应用之间不能互相污染全局样式、全局变量和路由。CSS 可以用 scoped CSS、CSS Modules、Shadow DOM 或统一命名空间；JS 侧要避免直接污染 `window`；路由要有统一前缀，比如 `/apps/order/*`、`/apps/hr/*`。某个子应用加载失败时，主应用要展示降级页，不能拖垮整个平台。

第六是公共能力和通信机制。平台可以提供统一 SDK，封装登录态获取、用户信息、权限判断、埋点、消息通知、文件上传、主题切换、页面跳转等能力。子应用通过 SDK 使用这些能力，不要每个业务部各自实现一套，否则后续很难治理。

第七是监控和审计。平台要能看到每个微应用的访问量、错误率、加载耗时、白屏情况、接口失败情况。发布、下线、权限变更也要有审计日志，方便排查“谁在什么时候改了什么”。内部平台也要做错误边界、超时降级和告警。

如果我负责落地，我会分阶段做：

1. **第一阶段做 MVP**：统一门户、应用注册、应用列表、SSO 登录、基础权限，先接入 1-2 个试点微应用。
2. **第二阶段做发布治理**：版本管理、灰度、回滚、审核流、接入规范文档和脚手架。
3. **第三阶段做平台化能力**：统一 SDK、监控告警、应用市场、权限申请、审计日志、接入质量检查。

面试里可以这样收口：这个平台不是简单做一个菜单聚合页，而是要解决多业务团队独立开发、独立发布、统一接入、统一权限、运行隔离、稳定监控和治理规范的问题。技术上可以用微前端承载，工程上要配套应用注册、发布流程、权限体系、SDK、监控和回滚机制，先用少量试点应用跑通，再逐步平台化。

这类题本质上不是考你会不会背某个框架，而是在考几种能力：

1. **需求拆解能力**：能不能把一句很大的需求拆成用户、角色、核心流程、边界和非目标。
2. **架构抽象能力**：能不能识别出平台层、业务层、运行时、发布链路、权限体系这些模块。
3. **工程落地能力**：能不能从 MVP、试点、灰度、回滚、监控这些角度说明怎么真正交付，而不是只画架构图。
4. **风险意识**：能不能提前想到隔离、权限、稳定性、性能、团队接入成本、后续治理这些问题。
5. **取舍能力**：比如微前端、iframe、Module Federation 不是谁绝对更好，而是要结合隔离要求、技术栈差异、体验和维护成本选择。

回答这类设计题，我可以套一个通用链路：

```text
先明确目标和角色
  -> 拆核心场景和流程
  -> 划分系统模块
  -> 设计关键数据和权限
  -> 说明技术方案和取舍
  -> 补充稳定性、监控、安全、扩展性
  -> 给出分阶段落地计划
  -> 用一句话总结核心价值
```

比如遇到“设计一个内部平台、低代码平台、插件平台、组件平台、运营配置平台”这类问题，都可以先问自己：

- 谁来使用？管理员、业务方、普通员工分别做什么？
- 核心对象是什么？应用、插件、组件、配置、流程还是数据？
- 生命周期是什么？创建、审核、发布、使用、监控、回滚、下线。
- 哪些能力要平台统一提供？登录、权限、配置、SDK、监控、发布、审计。
- 哪些能力留给业务自己实现？业务页面、业务接口、业务规则。
- 最容易出问题的点是什么？权限越权、发布事故、应用互相污染、不可回滚、无人负责。

面试表达上，不要一上来就说“我用 qiankun”。更好的顺序是：先讲业务目标和平台边界，再讲关键模块，最后再说具体技术选型。这样面试官会觉得你是在做系统设计，而不是只是在套一个技术名词。



## 高并发与缓存
### Next.js 中遇到高并发场景该怎么处理

答：

Next.js 遇到高并发时，核心不是单纯把 Node.js 进程开大，而是尽量减少请求到达应用层的次数，并把动态请求、缓存、数据库和降级策略分开处理。我一般按“静态化和缓存、服务无状态化、接口并发控制、数据层保护、可观测性”几层设计。

整体链路可以这样理解：

```text
用户请求
  -> CDN / Edge 缓存
  -> 命中则直接返回
  -> 未命中进入 Next.js
  -> 页面或 API 做鉴权、业务处理
  -> Redis / 数据库读取
  -> 返回并写入缓存
```

### 减少动态渲染

商品详情、活动页、帮助文档、SEO 落地页这类数据不是强实时的页面，我会优先使用 SSG 或 ISR，避免每个用户请求都触发一次服务端渲染。

```tsx
export const revalidate = 300
```

具体例子：

- **商品详情页**：商品标题、卖点、规格和 SEO 内容可以使用 SSG/ISR。第一次构建或缓存失效时从商品服务读取并生成页面，之后大量用户直接命中 CDN；价格和库存这类变化更快的数据，可以在页面加载后单独请求实时接口。
- **活动落地页**：大促页面通常在活动开始前就能确定内容，可以提前构建并预热 CDN。活动文案或 Banner 修改后，通过 `revalidatePath`、Webhook 或较短的 `revalidate` 触发更新，不需要每个访问者都重新执行 SSR。
- **帮助文档和 SEO 页面**：内容更新频率低，适合构建时生成静态 HTML，搜索引擎和用户都能直接拿到页面，不需要请求数据库。
- **实时订单页**：订单状态、用户优惠和库存不能直接做成长期静态页面。可以让页面框架静态化，但把用户相关数据放到鉴权后的动态接口中，并设置 `Cache-Control: private, no-store` 或按业务要求缓存。

商品详情页 ISR 示例：

```tsx
// app/products/[slug]/page.tsx
export const revalidate = 300

async function getProduct(slug: string) {
  const res = await fetch(`https://api.example.com/products/${slug}`, {
    next: {
      revalidate: 300,
      tags: [`product:${slug}`],
    },
  })

  if (!res.ok) {
    throw new Error('Failed to fetch product')
  }

  return res.json()
}

export default async function ProductPage({
  params,
}: {
  params: { slug: string }
}) {
  const product = await getProduct(params.slug)

  return (
    <main>
      <h1>{product.title}</h1>
      <p>{product.description}</p>
      <ProductPrice productId={product.id} />
      <ProductStock productId={product.id} />
    </main>
  )
}
```

这里商品标题、描述、规格这类信息走 ISR，5 分钟内大量请求可以命中缓存；价格和库存拆成独立组件或接口，避免为了一个实时字段让整个页面变成动态 SSR。

实时库存接口示例：

```ts
// app/api/products/[id]/stock/route.ts
import { NextResponse } from 'next/server'

export async function GET(
  request: Request,
  { params }: { params: { id: string } }
) {
  const stock = await getRealtimeStock(params.id)

  return NextResponse.json(
    { stock },
    {
      headers: {
        'Cache-Control': 'private, no-store',
      },
    }
  )
}
```

前端只局部刷新库存：

```tsx
'use client'

import { useEffect, useState } from 'react'

export function ProductStock({ productId }: { productId: string }) {
  const [stock, setStock] = useState<number | null>(null)

  useEffect(() => {
    fetch(`/api/products/${productId}/stock`)
      .then((res) => res.json())
      .then((data) => setStock(data.stock))
  }, [productId])

  if (stock === null) {
    return <span>库存加载中...</span>
  }

  return <span>库存：{stock}</span>
}
```

活动页主动刷新缓存示例：

```ts
// app/api/revalidate/route.ts
import { revalidatePath, revalidateTag } from 'next/cache'
import { NextResponse } from 'next/server'

export async function POST(request: Request) {
  const { secret, type, slug } = await request.json()

  if (secret !== process.env.REVALIDATE_SECRET) {
    return NextResponse.json({ message: 'Invalid token' }, { status: 401 })
  }

  if (type === 'product') {
    revalidateTag(`product:${slug}`)
  }

  if (type === 'campaign') {
    revalidatePath(`/campaigns/${slug}`)
  }

  return NextResponse.json({ revalidated: true })
}
```

这样运营修改商品或活动配置后，可以通过 CMS Webhook 调这个接口主动刷新缓存，不需要等自然过期，也不需要让所有用户请求都走 SSR。

请求链路对比：

```text
每次 SSR：
用户 -> Next.js -> 商品服务/数据库 -> 生成 HTML -> 返回

ISR/CDN：
第一次或缓存失效 -> Next.js -> 商品服务 -> 生成 HTML -> CDN 缓存
后续用户 -> CDN 直接返回 HTML

静态页面 + 实时模块：
用户 -> CDN 返回页面骨架
页面加载后 -> 客户端请求库存/订单接口 -> 更新局部 UI
```

如果是 Pages Router，也可以使用 `getStaticProps` 配合 `revalidate`。需要实时数据的部分再单独通过客户端请求或 Server Component 的动态请求获取，不让整页都变成动态渲染。

同时要注意避免无意中使用 `cookies()`、`headers()`、`no-store` 等能力，让原本可以缓存的页面退化成每次请求都重新生成。

### 使用 CDN 和分层缓存

- 静态 JS、CSS、字体、图片放 CDN，并使用带 hash 或版本号的 URL。
- SSG/ISR 页面尽量在 CDN 或边缘节点缓存。
- 热点接口可以使用 Redis 做短 TTL 缓存。
- 对商品、活动配置这类热点数据使用缓存预热，避免流量突然升高时所有请求同时回源。
- 缓存要设置失效和更新策略，避免活动改价、库存变化等数据出现脏读。

热点接口 Redis 缓存示例：

```ts
// app/api/products/[id]/summary/route.ts
import { NextResponse } from 'next/server'
import { redis } from '@/lib/redis'

const CACHE_TTL = 60

export async function GET(
  request: Request,
  { params }: { params: { id: string } }
) {
  const cacheKey = `product:summary:${params.id}`

  const cached = await redis.get(cacheKey)
  if (cached) {
    return NextResponse.json(JSON.parse(cached), {
      headers: {
        'X-Cache': 'HIT',
        'Cache-Control': 'public, s-maxage=60, stale-while-revalidate=120',
      },
    })
  }

  const product = await getProductSummaryFromDB(params.id)

  await redis.set(
    cacheKey,
    JSON.stringify(product),
    'EX',
    CACHE_TTL
  )

  return NextResponse.json(product, {
    headers: {
      'X-Cache': 'MISS',
      'Cache-Control': 'public, s-maxage=60, stale-while-revalidate=120',
    },
  })
}
```

这个例子适合商品摘要、活动配置、排行榜、推荐列表这类读多写少的数据。第一次请求 Redis 没命中，就回源查数据库，然后写入 Redis；后续 60 秒内同类请求直接走 Redis，减少数据库压力。

如果担心热点 key 同时失效导致缓存击穿，可以加一个短锁：

```ts
const lockKey = `lock:${cacheKey}`
const locked = await redis.set(lockKey, '1', 'NX', 'EX', 5)

if (!locked) {
  await sleep(100)

  const retryCached = await redis.get(cacheKey)
  if (retryCached) {
    return NextResponse.json(JSON.parse(retryCached), {
      headers: { 'X-Cache': 'HIT_AFTER_WAIT' },
    })
  }
}
```

实际项目里还会配合：

- TTL 增加随机抖动，避免大量 key 同时过期。
- 对热点数据提前预热，比如大促开始前写入 Redis。
- 数据更新时主动删除或更新缓存，避免长期脏数据。
- 对空结果设置短 TTL，防止恶意请求不存在的商品 ID 打穿数据库。

Next.js 构建产物可以使用长缓存：

```http
Cache-Control: public, max-age=31536000, immutable
```

HTML 或 ISR 页面则根据业务时效设置较短 TTL，必要时通过按标签失效或主动 revalidate 更新。

### 接口和服务保持无状态

Next.js 应用部署成多实例时，单个实例不能依赖本地内存保存登录态、任务状态或锁。需要把共享状态放到 Redis、数据库或专门的任务队列中，这样请求才能被负载均衡到任意实例。

部署层可以通过负载均衡扩容多个 Next.js 实例，并配合容器化、健康检查和滚动发布。实例只负责处理请求，不把本地文件、内存缓存当成唯一数据源。

### 控制接口并发和下游压力

服务端接口不能无限制地并行调用下游。对多个独立请求可以使用 `Promise.all`，但要配合超时、并发上限和错误处理：

```tsx
const controller = new AbortController()
const timeout = setTimeout(() => controller.abort(), 3000)

try {
  const response = await fetch(url, {
    signal: controller.signal,
    next: { revalidate: 60 },
  })

  if (!response.ok) {
    throw new Error(`Request failed: ${response.status}`)
  }

  return await response.json()
} finally {
  clearTimeout(timeout)
}
```

对搜索、推荐、报表等高成本接口，要增加限流、请求合并、去重和降级策略。比如同一时间大量请求同一个热点商品时，可以只允许一个请求回源，其余请求等待或读取缓存，避免缓存击穿。

常见保护策略包括：

- 网关或 API 层限流：按 IP、用户、接口和租户维度限制。
- 超时和重试：只对可重试错误进行有限次数重试，并使用退避。
- 熔断和降级：推荐、评论、埋点等非核心能力失败时，不阻塞商品主流程。
- 幂等：下单、支付回调、库存扣减等写操作使用幂等键，避免重试造成重复操作。
- 请求体和分页限制：防止一次请求拉取过大数据量。

### 保护数据库和共享服务

高并发下最容易先被打满的通常是数据库连接池、慢查询和 Redis，而不是页面组件本身。我会：

- 给数据库连接池设置上限，避免每个 Next.js 实例都无限创建连接。
- 优化索引和慢查询，避免在请求链路中做大范围扫描。
- 使用 Redis 缓存热点读数据，给缓存设置合理 TTL。
- 对库存、订单等强一致写操作使用事务、乐观锁或原子命令。
- 将发邮件、生成报表、图片处理等耗时任务放到异步队列，不阻塞接口响应。
- 对数据库和 Redis 增加连接、命中率、延迟、错误率监控。

### 前端体验和流式返回

对于页面首屏，我会用 Server Component、流式渲染和 Suspense，让页面先返回可用的骨架和核心内容，慢模块后续补齐。这样不能替代后端扩容，但可以降低用户感知等待时间。

```tsx
<Suspense fallback={<ProductSkeleton />}>
  <ProductRecommendations />
</Suspense>
```

推荐、评论、客服等非核心模块不要阻塞主内容；图片、JS 和第三方脚本继续按首屏优先级加载，避免高并发时所有用户同时加载大量非关键资源。

### 监控和压测

上线前会用压测工具模拟峰值流量，并重点观察：

- QPS、P95/P99 延迟、错误率和超时率；
- Next.js 实例 CPU、内存、事件循环延迟；
- CDN 命中率和回源比例；
- Redis 命中率、连接数和慢命令；
- 数据库连接池、慢查询、锁等待；
- 下游接口的成功率和耗时。

通过这些指标判断瓶颈到底在 CDN、Next.js SSR、Node 事件循环、数据库还是第三方服务，而不是只看单个页面的 Lighthouse 分数。

面试表达：

> Next.js 高并发的处理思路是先减少动态请求，再保护应用和下游。静态或低频变化页面用 SSG/ISR 和 CDN 缓存，热点数据用 Redis，应用保持无状态并通过负载均衡扩容；动态接口增加超时、限流、幂等、熔断和降级，数据库侧控制连接池、优化慢查询，耗时任务放入异步队列。最后通过压测和监控观察 QPS、P99、错误率、缓存命中率、事件循环延迟和数据库连接池，定位真实瓶颈并持续调优。

## AI规范和方法论
### AI 使用心得
- 需求需要边界，一个功能一个commit

### 对于 SDD，比如 OpenSpec 带来的额外文档，该怎么看待

答：

我不会把 SDD 产生的文档简单看成额外负担，而是看它是否降低了后续沟通、实现和维护成本。OpenSpec 这类工具把需求、设计、规格和任务拆解显式沉淀下来，虽然增加了前期文档动作，但能减少“理解不一致、边做边改、遗漏验收条件”这类隐性成本。

我一般会按变更规模分层使用：

- 小改动：只保留简短的需求说明和验收标准，不为了流程完整而生成大量文档。
- 中等功能：补充方案、接口约束、数据流和任务清单，让实现边界清楚。
- 跨模块或高风险改动：保留完整的 proposal、design、spec 和 tasks，必要时补充迁移、回滚和验证方案。

对 OpenSpec 来说，文档不是写完就结束，而是研发过程中的协作契约：

```text
模糊需求
  -> proposal：明确目标、范围和非目标
  -> design：确定架构、数据流和技术取舍
  -> spec：把行为和验收条件写清楚
  -> tasks：拆成可执行、可验证的开发任务
  -> implementation：按任务落地
  -> verification：测试、构建和验收
  -> archive：沉淀变更历史
```

它的价值主要有三点：

1. **降低沟通成本**：产品、前端、后端和测试可以围绕同一份约束对齐，减少口头信息丢失。
2. **提升 AI 协作质量**：AI 不只拿到一句模糊需求，而是能基于规格和任务逐步实现，减少上下文漂移和重复返工。
3. **保留决策和演进记录**：后续排查问题、交接或继续迭代时，可以知道当时为什么这样设计，而不只是看到最终代码。

当然，文档也要控制成本。不能为了“形式上遵循 SDD”而复制代码、重复描述，或者把已经失效的文档长期留在主流程里。我的判断标准是：这份文档是否能帮助别人更快理解、实现、测试或维护。如果不能，就应该合并、缩短或删除；如果需求会影响多个模块、接口契约或线上稳定性，那么这部分文档成本通常是值得的。

面试表达：

> 我认为 SDD 带来的文档不是纯粹的额外成本，而是把需求、设计决策和验收标准显性化。以 OpenSpec 为例，我会根据变更风险分层使用：小改动保持轻量，中大型或跨模块需求才完整保留 proposal、design、spec 和 tasks。这样既避免流程形式主义，又能降低沟通和返工成本，同时为 AI 辅助开发提供稳定上下文。最终我会用测试、构建和验收结果验证文档是否真正服务于交付。
