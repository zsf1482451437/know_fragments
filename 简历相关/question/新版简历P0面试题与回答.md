## Q5：你们自研 SSR 的完整链路是什么？

### 面试官考察点

是否真正理解 SSR，而不只是使用过框架 API。

### 推荐回答

完整链路可以概括为六步。

第一，请求进入 Node.js SSR 服务后，根据 URL 完成路由匹配，确定页面组件和页面所需数据。第二，服务端调用 BFF 或下游接口完成商品、活动等数据预取。第三，使用 React 服务端渲染能力将页面组件和初始数据生成 HTML。第四，将 HTML、SEO Meta、当前路由对应的 JavaScript 和 CSS 注入模板。第五，把服务端使用的初始数据序列化到 `window.__INITIAL_DATA__`。第六，浏览器加载客户端代码后，复用同一份数据完成 Hydration，再接管后续交互。

这个链路的核心不是“服务端返回字符串”，而是保证服务端 HTML、初始数据和客户端首次渲染一致。同时还要处理请求级数据隔离、接口异常降级和序列化安全，避免不同用户数据串用或注入脚本风险。

### 二次追问要点

- 每个请求创建独立上下文，不能复用可变全局状态。
- 动态数据应序列化并转义后再注入 HTML。
- 接口失败时按页面重要性选择局部降级或 CSR 兜底。

### 回答边界

- 如果底层 SSR 框架不是个人从零设计，应表述为“参与链路建设和页面接入”。
- 不把 SSR 直接等同于页面性能一定更好，需同时关注 TTFB 和服务端压力。

## Q6：如何保证服务端渲染和客户端 Hydration 一致？

### 面试官考察点

是否理解 Hydration mismatch 的来源和治理方式。

### 推荐回答

核心原则是让服务端和客户端首次渲染使用相同的组件树和初始数据。

数据层面，服务端预取完成后，把同一份结果注入 `window.__INITIAL_DATA__`，客户端初始化状态时优先复用，而不是立刻重复请求。渲染层面，首屏不能直接依赖 `window`、`document`、本地时间、随机数等只在客户端稳定存在的值；确实依赖浏览器环境的逻辑放到 `useEffect` 中执行。

对于登录态、价格、库存等可能快速变化的数据，我会先保证首次渲染与服务端一致，Hydration 完成后再发请求校准。列表渲染要保证 Key 稳定，日期和多语言格式化也要保证服务端与客户端使用相同的时区和语言配置。

如果出现 mismatch，我会先看控制台报错对应节点，再对比页面源码和客户端首次渲染结果，检查数据、条件分支、时间随机值和不合法 DOM 嵌套。

### 二次追问要点

- 不在渲染阶段直接读取浏览器专属 API。
- 用户态数据避免服务端一套、客户端初始化另一套。
- 必须区分首次 Hydration 和 Hydration 后的数据刷新。

### 回答边界

- 不用 `suppressHydrationWarning` 掩盖普遍性问题。
- 不承诺所有实时字段在 SSR 时绝对最新，应说明后续校准策略。

## Q7：为什么需要 BFF？它和核心后端服务的边界是什么？

### 面试官考察点

是否理解 BFF 的业务价值和架构边界。

### 推荐回答

跨境商城页面通常需要商品、价格、库存、活动、用户和推荐等多个服务的数据。如果前端直接调用所有服务，会产生请求次数多、协议不一致、字段冗余、鉴权逻辑分散等问题。

BFF 的职责是面向页面场景做接口编排。比如商品详情页接口可以并行请求商品基础信息、区域价格、库存和活动，再裁剪成前端需要的统一结构；同时集中处理会话透传、参数校验、错误码映射、Trace ID 和部分聚合缓存。这样前端关注页面状态，不需要理解每个下游服务的协议差异。

它与核心后端的边界也很明确：BFF 不拥有商品、订单、库存等核心领域数据，不直接定义订单状态机，也不替代领域服务完成订单创建和状态变更。核心规则和数据一致性仍由对应领域服务负责，BFF 负责调用、组合和面向前端的适配。

### 二次追问要点

- 聚合接口可并行请求无依赖的下游，降低总耗时。
- BFF 统一面向前端的 DTO，不直接暴露下游内部模型。
- 业务规则应根据所有权放在 BFF 或领域服务，不能全部堆在 BFF。

### 回答边界

- 不说 BFF 直接管理订单数据库。
- 不把 BFF 描述成简单反向代理，它还承担页面级编排和协议适配。

## Q8：BFF 如何处理缓存、超时、重试和降级？

### 面试官考察点

是否具备稳定性意识，能否说明具体策略和取舍。

### 推荐回答

我会先按数据实时性和业务重要性分类，而不是统一套一套策略。

商品详情、活动配置等读多写少的聚合结果可以使用 Redis 缓存，并设置合理 TTL；数据发生变化时由业务事件或管理操作触发主动失效，缓存未命中再回源。价格、库存这类强实时数据会缩短缓存时间或直接请求权威服务，不能只依赖长 TTL。

每个下游调用都需要超时控制，避免一个慢服务拖住整个聚合接口。重试只用于幂等读请求或明确可重试的瞬时错误，设置有限次数和退避，写操作不能无条件重试。降级上会按字段重要性处理：推荐、评价等非核心模块失败可以返回空数据；商品主体或关键交易信息失败则返回明确错误，不能伪造成功。

同时通过 Trace ID、结构化日志记录下游耗时、状态码和降级结果，方便定位是 BFF、网络还是具体下游服务的问题。

### 二次追问要点

- 防止缓存击穿可使用请求合并、互斥更新或短期兜底值。
- 只重试幂等请求，避免放大流量和重复写入。
- 降级结果应在响应中可识别，便于前端选择展示方式。

### 回答边界

- 不笼统地说“所有接口失败都重试三次”。
- 不用缓存覆盖订单最终状态、支付结果等权威数据。

## Q9：商品、SKU、库存后台如何设计前后端协作？

### 面试官考察点

是否理解商城后台业务，而不只是实现表格和表单。

### 推荐回答

前端首先要把商品、SKU 和库存三个层级区分清楚。商品承载标题、分类、描述等公共信息；SKU 是具体规格组合，拥有独立编码、价格和可售状态；库存通常与 SKU、仓库或区域关联。

后台页面会围绕运营任务设计，包括组合条件检索、商品详情、SKU 批量编辑、上下架和库存维护。前端使用稳定的表单模型和类型定义组织数据，批量操作时先展示影响范围并要求确认，提交后展示任务进度、成功失败数量和错误明细，而不是只给一个“操作成功”提示。

BFF 负责把不同下游返回的商品、分类、价格和库存字段适配成统一 DTO，完成参数校验、会话和资源权限校验，再调用对应领域服务。真正的商品规则、库存扣减和最终数据一致性由下游服务维护。

### 二次追问要点

- SKU 唯一标识不能依赖前端展示文案。
- 批量任务需要任务 ID、进度、失败原因和可重试范围。
- 列表筛选条件应与 URL 或查询状态同步，便于返回和分享。

### 回答边界

- 不把库存最终一致性描述成前端或 BFF 的职责。
- 不只讲表格组件，要讲运营流程、异常反馈和权限。

## Q10：运营后台的 RBAC、资源权限和审计怎么做？

### 面试官考察点

是否理解“隐藏按钮不等于权限控制”，能否覆盖鉴权和追溯。

### 推荐回答

权限控制分为前端展示、BFF 校验和下游领域校验三个层次。

前端根据当前用户的权限点控制菜单、路由和操作入口，让用户只看到可执行功能，但这只是体验层。BFF 收到商品修改、批量上下架、订单处理或售后审核请求后，需要验证会话、角色权限、资源范围和请求参数，不能相信前端传入的用户身份。涉及核心领域规则时，下游服务还要执行最终校验。

审计方面，关键操作要记录操作者、目标资源、动作、请求标识、时间和结果。对于修改类操作，可以透传变更前后信息或业务审计上下文，由统一审计链路落库。这样出现误操作或权限争议时，可以通过 Trace ID 和审计记录还原链路。

高风险批量操作还应增加二次确认、影响范围提示和任务结果明细，必要时提供撤销或补偿方案。

### 二次追问要点

- RBAC 解决角色到权限点映射，资源权限解决“能操作哪一条数据”。
- 前端权限用于体验，服务端权限才是安全边界。
- 审计日志应避免记录密码、Token 等敏感信息。

### 回答边界

- 不说前端隐藏按钮后接口就安全了。
- 不声称 BFF 可以绕过下游服务的核心业务校验。

## 三、GogoalShop 跨境商城

## Q11：你是如何定位并解决首页性能问题的？

### 面试官考察点

是否具备“测量、定位、优化、验证”的完整性能治理方法。

### 推荐回答

我没有先凭经验改代码，而是先建立基线。通过 Lighthouse 和 Web Vitals 看 LCP 等体验指标，用 Performance 和 Network 瀑布流判断瓶颈来自网络、主线程还是渲染，再用 `@next/bundle-analyzer` 分析首页路由的 JavaScript 组成。

当时主要问题是首屏 JavaScript 体积大、非首屏模块过早加载、图片和字体资源重，以及客服、评论、营销和追踪脚本占用主线程。针对这些问题，我做了路由和组件级代码分割、依赖替换与 Tree Shaking，使用 `next/dynamic` 延迟加载非首屏模块，通过 `next/image`、`next/font` 优化图片和字体，并按页面和触发时机治理第三方脚本。

优化后，首页关键 JavaScript 从 3MB 降到 600KB，LCP 从 4 秒降到 2 秒以内，跳出率从 30% 降到 20%。最后用相同设备、网络和缓存条件复测，避免前后口径不一致。

### 二次追问要点

- LCP 拆为 TTFB、资源加载延迟、资源下载时长、元素渲染延迟。
- 实验室数据用于定位，真实用户数据用于判断线上分布。
- 优化前后应保持页面、网络、设备和缓存条件一致。

### 回答边界

- 不只说“用了懒加载和压缩”。
- 如果指标不是全站线上 P75，应说明是首页重点场景的阶段性结果。

## Q12：关键 JavaScript 从 3MB 降到 600KB，具体做了什么？

### 面试官考察点

指标是否真实，能否说清包体治理的技术动作。

### 推荐回答

我先区分构建产物大小和用户首次访问实际下载量。通过 Next.js 构建输出和 bundle analyzer 找出首页首屏 Chunk 中占比较大的依赖，再用 Network 看首次加载的 transfer size，并用 Coverage 检查大量下载但首屏未执行的代码。

具体优化包括四类。第一，通过 `next/dynamic` 将营销弹窗、评论、推荐和非首屏楼层拆出首屏。第二，治理 lodash、图标库等依赖的导入方式，替换过重依赖并确保 Tree Shaking 生效。第三，将只在特定页面使用的第三方脚本改为按页加载或交互后加载。第四，检查重复依赖和客户端边界，避免把本可在构建期或服务端完成的逻辑全部打入客户端。

优化后再次对比首页必须加载的 Chunk 和实际 Network 请求，确认 3MB 到 600KB 是关键页面首次加载成本下降，而不是简单删除 Source Map 或只比较压缩前后两个不同口径。

### 二次追问要点

- `import _ from 'lodash'` 与按函数导入可能影响 Tree Shaking。
- 动态加载需要结合首屏必要性，不能把核心内容全部延后。
- 包体下降后还要看解析执行时间和 Long Task。

### 回答边界

- 不把整个仓库产物体积说成首屏实际下载量。
- 不为了数字删除必要功能或影响 SEO 内容。

## Q13：商城页面如何选择 SSG、ISR 和 CSR？

### 面试官考察点

能否根据 SEO、实时性、性能和成本做渲染策略取舍。

### 推荐回答

我按页面内容稳定性、SEO 诉求、用户态和更新频率选择。

品牌内容页、解决方案页和相对稳定的活动页适合 SSG，构建时生成 HTML，访问性能好、服务端压力低。商品详情或活动内容需要较快更新，但又希望保留静态页面性能时，可以使用 ISR，通过再验证周期或主动刷新更新页面。价格、库存、购物车、登录态等强实时或用户相关数据使用 CSR 在客户端请求，避免把整页都变成每次请求动态渲染。

实际页面通常是混合策略：商品标题、描述、主图和 SEO 信息通过 SSG/ISR 输出，价格、库存和用户态在客户端校准。这样同时兼顾可索引内容、首屏体验、数据新鲜度和服务成本。

### 二次追问要点

- ISR 需要接受短时间旧数据，并设计失效策略。
- 用户敏感数据不能被错误地静态化并共享。
- 强实时字段要明确权威数据源和刷新时机。

### 回答边界

- 不说商品页只能使用某一种渲染方式。
- 不把 SSG 描述为完全不需要客户端 JavaScript。

## Q14：多语言和跨境 SEO 是怎么落地的？

### 面试官考察点

是否理解国际化不仅是翻译文案，还涉及路由、索引和内容治理。

### 推荐回答

项目使用 `[locale]` 路由和 `next-intl` 管理多语言。文案按语言拆分为独立 messages 资源，服务端根据路由加载对应字典，客户端切换语言时跳转到对应 locale 路由，同时提供默认语言和缺失 Key 兜底。

SEO 方面，每种语言生成对应的 title、description 和 Open Graph 信息；通过 `hreflang` 告诉搜索引擎不同语言版本的对应关系，通过 canonical 明确当前页面的规范地址。页面只保留一个主 H1，商品卖点、规格和 FAQ 使用清晰层级，核心内容在预渲染 HTML 中可见。

同时要处理日期、货币、数字格式和地区差异，不能只翻译字符串。验收时会检查页面源码、语言切换、缺失文案、Meta、`hreflang` 和不同视口表现。

### 二次追问要点

- locale 应进入路由和缓存 Key，避免返回错误语言内容。
- 翻译资源按语言拆分，避免所有语言包进入首屏。
- canonical 与 `hreflang` 解决的问题不同，不能相互替代。

### 回答边界

- 不把机器翻译等同于完整国际化。
- 不承诺仅靠 Meta 就能保证自然流量增长。

## 四、Shopify 自研应用

## Q15：为什么要自研 Shopify 应用？业务价值是什么？

### 面试官考察点

是否能从业务问题出发，而不是只介绍技术实现。

### 推荐回答

当时商品定制和黑名单下单拦截依赖第三方付费应用，但通用插件的规则扩展能力有限，而且长期订阅成本较高。团队希望把核心规则掌握在自己手里，因此决定自研。

我独立交付了自定义印号 TT-Options 和黑名单下单拦截 TTBlacklist - Order Guard 两款应用。前端使用 React、Vite 和 TypeScript 实现配置页面，通过 Shopify Admin API 和 GraphQL 获取商品、订单等平台数据，使用 Prisma 持久化店铺配置、规则和操作记录，并通过 Docker 和 Shell 脚本完成部署与发布。

最终两款应用完成上线并替代第三方工具，年节省数万元订阅成本。发布流程从 5 步简化为 1 步，镜像化部署也减少了本地和服务器环境不一致的问题。

### 二次追问要点

- 自研前要评估开发维护成本是否低于订阅与受限成本。
- 配置和规则属于应用数据，Shopify 商品订单属于平台数据。
- 上架要处理权限范围、回调地址、隐私政策和环境配置。

### 回答边界

- 不只讲“省钱”，还要说明定制能力和后续维护责任。
- 不把 Shopify 平台数据说成全部存入自建数据库。

## Q16：Shopify 应用的 GraphQL、Prisma 和 Docker 分别解决什么问题？

### 面试官考察点

是否真正完成了从平台接口、应用数据到部署的完整链路。

### 推荐回答

三者分别解决平台交互、应用持久化和运行环境一致性。

GraphQL 用于调用 Shopify Admin API，根据应用权限读取或修改商品、客户、订单等平台资源。调用时要控制查询字段和分页，处理限流、权限不足和接口错误，不能把平台内部结构直接暴露给页面。

Prisma 管理应用自己的数据，比如店铺配置、商品定制规则、黑名单规则和操作记录。通过 Schema 定义关系和约束，再由服务层组织查询与更新。敏感信息和 Shopify Secret 不写入前端或镜像。

Docker 固化 Node.js 版本、依赖和启动方式，解决服务器环境不一致问题。环境变量在运行时注入，镜像不包含 Secret；Shell 脚本负责构建、版本和发布步骤，使发布从人工 5 步简化为 1 步。

### 二次追问要点

- GraphQL 需要处理游标分页和请求成本。
- Prisma Migration 要区分开发和生产执行方式。
- Docker 可通过多阶段构建减少最终镜像体积。

### 回答边界

- 不说 GraphQL 天然比 REST 更快，优势是按需查询和类型化协议。
- 不把 Secret 写入代码仓库、前端环境变量或 Dockerfile。

## 五、喜动商城个人全栈项目

## Q17：为什么使用 Go 分层？各层职责是什么？

### 面试官考察点

是否真正理解后端分层，而不是只会创建目录。

### 推荐回答

我采用 `handler -> service/domain -> repository` 分层，目的是隔离 HTTP、业务规则和数据访问。

Handler 负责解析请求、Schema 校验、读取会话身份、调用 Service，并把领域错误转换成统一 HTTP 响应。Service 或 Domain 层负责业务用例和规则，例如结算时校验商品、生成价格快照、扣减库存、创建订单，不依赖具体 HTTP 框架。Repository 负责 MySQL 查询、事务内数据操作和模型映射。

这样做的价值是业务逻辑可以脱离 HTTP 做单元测试，数据访问实现也可以替换。事务边界由 Service 层根据完整业务用例控制，但具体 SQL 通过 Repository 执行，避免 Handler 直接拼 SQL 或 Repository 承担跨领域流程。

### 二次追问要点

- 统一错误应保留领域错误码，不直接把数据库错误暴露给客户端。
- Repository 接收事务对象后，事务内所有写操作必须复用同一连接。
- 简单查询不需要为了分层制造过多抽象。

### 回答边界

- 不把分层说成固定模板，要说明它解决了什么耦合问题。
- 不在 Handler 中实现结算和库存规则。

## Q18：结算事务如何避免超卖、重复下单和脏订单？

### 面试官考察点

对事务边界、并发控制和幂等是否有完整理解。

### 推荐回答

结算链路需要把价格确认、库存扣减和订单创建放在一个明确事务中。

请求进入后，服务端从 Session 获取用户身份，不能相信客户端传入的 userId。事务内重新查询商品和 SKU 的有效状态及当前价格，生成订单价格快照；库存扣减使用带条件的原子更新，例如只有 `stock >= quantity` 才执行 `stock = stock - quantity`，再检查受影响行数。随后写入订单、订单项和订单时间线，最后清理已选择的购物车项。任一步失败都回滚，避免库存扣了但订单没创建。

防止重复提交时，客户端生成或服务端接收幂等 Key，并和用户及业务结果绑定。相同 Key 的重复请求直接返回第一次结果，而不是再次扣库存。数据库层还可以使用唯一约束兜底，防止并发请求同时创建重复订单。

### 二次追问要点

- 价格必须以服务端查询和快照为准。
- 条件更新或行锁用于处理并发库存，不能先查后无条件更新。
- 外部支付调用不应长时间占用数据库事务，可通过状态机和异步确认衔接。

### 回答边界

- 不说单靠前端禁用按钮可以防重复下单。
- 不把 Redis 分布式锁当成所有库存问题的唯一答案。

## Q19：Session、Redis 和资源归属校验是如何设计的？

### 面试官考察点

认证、权限、缓存和多用户数据隔离是否真正闭环。

### 推荐回答

登录成功后，服务端创建随机 Session ID，将用户 ID、角色和过期时间写入 Redis，再通过 HttpOnly、Secure、SameSite Cookie 返回 Session ID。后续请求由认证中间件读取 Cookie，从 Redis 恢复身份，并把用户上下文传给业务层。

权限分两层。第一层是角色权限，例如普通用户不能访问后台接口；第二层是资源归属，例如查询订单、地址、购物车或智能体会话时，Repository 条件必须同时包含资源 ID 和当前 Session 派生的 userId，不能先按 ID 查询后只在前端判断。

Redis 还用于商品读缓存，但 Session 与业务缓存使用不同 Key 前缀和 TTL。商品更新后执行主动失效，缓存未命中再回源 MySQL。登出时删除 Session，敏感操作可以额外校验权限和进行二次确认。

### 二次追问要点

- HttpOnly 降低 Token 被脚本读取的风险，但仍要防 CSRF。
- Session 续期可采用滑动过期，同时设置最大生命周期。
- 缓存 Key 要包含会影响结果的维度，用户私有数据不能误用公共缓存。

### 回答边界

- 不从请求参数直接信任 userId。
- 不把 Redis 当作订单等核心数据的唯一持久化存储。

## Q20：AI Agent 与 RAG 如何保证安全、可控和可恢复？

### 面试官考察点

是否真正理解 AI 工程化中的权限、幻觉、工具调用和会话恢复。

### 推荐回答

我把模型定位为决策和交互层，不让它直接拥有数据库或任意接口权限。

RAG 链路中，先将 README、业务文档和 OpenSpec 规范切块并生成 Embedding，写入 Qdrant。用户提问后检索相关片段，把内容和来源一起交给模型，回答中返回引用，降低无依据回答。知识库只提供上下文，涉及商品和订单实时数据时仍调用只读业务工具。

工具层采用白名单和结构化参数校验，每个工具在服务端重新做会话、角色和资源归属校验，不能因为模型生成了某个 userId 就直接执行。支付、取消、退款等高风险动作需要二次确认和幂等 Key；后台智能体默认只读。

输出通过 SSE 发送 `thinking`、`tool_call`、`tool_result`、`citation`、`delta`、`done` 和 `error` 等事件。会话和消息持久化到数据库，刷新后按用户身份恢复；中断或工具失败时返回明确事件，前端可以保留已完成内容并提示重试。

### 二次追问要点

- Prompt 约束不能替代服务端鉴权。
- 检索结果需要来源、相关性阈值和无结果兜底。
- SSE 断开后应停止无意义生成，并记录消息最终状态。

### 回答边界

- 不声称 RAG 能完全消除幻觉。
- 不允许模型绕过正常业务 Service 直接读写数据库。
