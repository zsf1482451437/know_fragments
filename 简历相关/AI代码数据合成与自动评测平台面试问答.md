# AI 代码数据合成与自动评测平台面试问答

## 使用说明

- 项目统一表述为“AI 代码数据合成与自动评测平台”，不披露内部项目代号、域名、密钥和业务数据。
- 回答顺序建议采用“背景 -> 问题 -> 方案 -> 结果 -> 边界”。
- 代码可以证明系统实现，但不能证明个人贡献。个人职责应以实际参与范围为准，不把团队成果包装成个人独立完成。
- 没有完成统一实验的数据不编造提升比例，应说明当前观测指标和量化方法。

## 一、项目背景与价值

### Q1：这个平台解决什么问题？

推荐回答：

这是一个面向仓库级代码生成的数据生产和自动评测平台。输入包括用户需求、初始仓库、技术栈、模型及产线配置，平台在隔离沙箱中驱动 Agent 探索仓库、修改代码、启动服务并执行验证，最后输出代码结果、完整轨迹和质量信号。

它解决的核心问题是：一次模型调用无法可靠完成仓库级任务，而为每种模型、技术栈和评测方式分别开发产线又会产生大量重复代码。CommonFrameworkV1 将共性流程抽成可配置生命周期，让不同场景共享执行骨架。

### Q2：数据合成具体合成什么？

推荐回答：

合成结果不只是最终代码，还包括：

- 原始需求和泛化后的需求；
- 模型思考、工具调用和工具执行结果；
- 文件读取与修改轨迹；
- 最终仓库或构建产物；
- checklist、Playwright 或 Flutter 测试；
- 构建、静态分析、功能和 Rubrics 等质量信号。

因此它既是代码执行系统，也是训练与评测数据的生产系统。

### Q3：为什么需要平台化产线，而不是人工运行 Agent？

推荐回答：

人工运行难以批量复现，模型版本、Prompt、沙箱环境和检查标准也难保持一致。平台把输入、模型协议、工具执行、后置验证、评分和交付固定为可追踪流程，使任务可以批量调度、失败归因和版本对比。

人工仍然适合抽检和维护黄金样本，但不适合作为大规模数据生产的主链路。

### Q4：平台最终服务训练、评测还是样本筛选？

推荐回答：

三者都可以服务，但消费的数据不同。代码、对话和工具轨迹可以用于训练或行为分析；测试结果和 Rubrics 可以用于模型评测；`checkSignal`、`pass_rate` 和错误信息可以用于样本筛选。

平台层不把某一种用途写死，而是统一沉淀过程和结果，由下游按场景消费。

### Q5：如何判断一条合成数据有效？

推荐回答：

首先看任务是否完整结束、沙箱和仓库状态是否可用；其次看应用能否启动或构建；再看功能 E2E、静态分析、视觉或 Rubrics 等检查结果；最后检查轨迹是否存在严重工具错误、无效循环或危险修改。

当前框架会把参与评分的检查结果写入 `checkSignal`，再计算 `pass_rate`。但有效性不应只依赖平均分，构建失败和核心功能失败更适合作为阻断门禁。

### Q6：它相比普通代码生成 Agent 多了什么？

推荐回答：

普通 Agent 关注“完成一次代码修改”，这个平台还提供：

- 配置驱动的生命周期和节点注册；
- NFC、XML、JSON 工具协议适配；
- Mars/VKE 沙箱与 Git 环境初始化；
- 多技术栈启动和构建节点；
- checklist、Playwright、Flutter 和 Rubrics 验证；
- 质量信号、过程监控、产物上传和批量筛选。

核心差异是把模型自主执行放进了可控制、可验证、可追踪的工程链路。

## 二、个人职责与产出

### Q7：你具体负责哪些部分？

推荐回答：

我参与 CommonFrameworkV1 产线建设，工作重点围绕节点能力优化和自动评测闭环，包括输入上下文增强、模型与工具调用后的执行纠偏、Playwright checklist 测试生成、测试执行反馈，以及外部评测节点的重试和错误治理。

通用引擎、模型接入和沙箱基础设施是团队共同建设。我会明确区分团队架构与我重点参与的节点。

### Q8：CommonFrameworkV1 已经存在，你主要优化什么？

推荐回答：

我的重点不是重写总控引擎，而是在生命周期中补齐高价值节点：

- 输入阶段提升 Prompt、Knowledge 和仓库上下文质量；
- Agent 阶段拦截机械错误并回填真实执行结果；
- `afterTraceEnd` 阶段支持完成后的二次修复；
- 测试阶段把 checklist、真实代码、脚本生成、Lint 和执行结果串成闭环；
- 稳定性阶段补充有限重试、错误分类和过程日志。

### Q9：“产线节点化迭代”体现在哪里？

推荐回答：

框架通过 `Steps` 定义生命周期，每个节点实现统一的 `BaseNode` 协议，并通过节点 ID 和参数挂载到指定阶段。新增能力通常只需实现节点、注册节点，再在产线配置中组合，无需复制完整 Pipeline。

我的产出应围绕具体节点讲，例如测试生成、执行反馈或稳定性治理，而不是笼统说“负责整个框架”。

### Q10：哪些是你主导，哪些是协作？

推荐回答：

建议按真实情况回答。可以表述为：我重点推进自动测试与稳定性相关节点，包括 checklist 到 Playwright 的生成、Lint 重试、沙箱执行和结果回写；框架总控、沙箱 SDK、模型服务和外部评测服务由团队协作完成。

面试中不要仅用“参与”或“负责”，要说清设计、编码、联调和验证分别做到什么程度。

### Q11：最核心的个人产出是什么？

推荐回答：

我认为最核心的产出是把“模型认为完成”升级为“平台有验证证据”。通过需求 checklist、真实仓库探索、测试脚本生成、Lint 校验、真实执行和失败反馈，形成可复用的自动验证链路。

它让样本筛选不再只依赖最终文件或模型的 `finish`，而是具备功能测试和过程证据。

### Q12：如果删除你负责的部分，系统会退化什么？

推荐回答：

代码 Agent 仍然可以修改仓库，但自动评测可信度和稳定性会下降：测试脚本更容易出现语法错误或臆造选择器，测试失败难与需求步骤映射，外部服务瞬时异常也更容易导致整条任务失败。

最终结果可能只能证明“生成了代码”，不能充分证明“需求被正确实现”。

## 三、CommonFrameworkV1 架构

### Q13：完整执行链路是什么？

推荐回答：

完整链路是：

```text
初始化 CommonState
-> 处理上游产线输入
-> 注册 Knowledge 和 Nodes
-> generalizePrompt 泛化需求
-> 创建 Sandbox
-> 初始化 Git 和依赖环境
-> 初始化对话
-> beforeEnterTrace
-> Agent 主循环
   -> 模型调用
   -> afterModelCall
   -> beforeToolCall
   -> 沙箱执行工具
   -> afterToolCall
   -> 结果回填模型
-> finish
-> afterTraceEnd
-> startService
-> commonChecker
-> genUnitTest
-> runUnitTest
-> beforeFinish
-> computeSignal
-> 释放沙箱并返回结果
```

模型调用 `finish` 只是主循环结束条件，不等于平台验收完成。

### Q14：`generalizePrompt`、Agent 主循环和 `afterTraceEnd` 分别做什么？

推荐回答：

`generalizePrompt` 将模糊场景扩展成具体需求，并补充技术栈约束。Agent 主循环负责模型调用、工具解析、沙箱执行和结果回填。`afterTraceEnd` 在模型调用 `finish` 后运行，可通过 `style_fix` 或 `query_add` 增加下一轮任务，让 Agent 继续修复或扩展。

三者分别解决“任务定义、任务执行、完成后纠偏”。

### Q15：为什么拆成生命周期节点？

推荐回答：

不同产线主要差异在模型、技术栈、检查器和容错策略。如果全部写在主循环里，会形成大量条件分支。生命周期节点将差异放到明确阶段，既保留统一主干，也允许产线按配置组合。

节点化还便于记录耗时、单独失败和复用能力。

### Q16：节点如何注册和执行？

推荐回答：

框架维护节点注册表、节点实例 Map 和参数 Map。启动时遍历 `Steps`，实例化各阶段候选节点，根据 `question.steps` 中配置的 ID 挂载 Hook。执行阶段调用 `trigger(step)`，按配置顺序执行节点；节点返回非 `next` 动作时会提前改变控制流。

配置了不存在的节点 ID 会在注册阶段直接报错。

### Q17：State 如何传递？如何避免污染？

推荐回答：

一次任务对应一个 `CommonState`，保存问题配置、消息、代码轨迹、当前工具调用、沙箱、端口、检查结果和监控数据。节点通过上下文读写同一个 State。

优点是节点衔接简单，风险是隐式覆盖。当前通过任务级实例、固定字段和 `extra.<nodeId>` 命名减少冲突，但长期还应加强字段所有权、不可变更新和阶段输入输出 Schema。

### Q18：如何支持不同技术栈？

推荐回答：

通用引擎只处理生命周期、模型、工具和状态，技术栈差异通过配置和节点隔离。例如启动阶段有 Vite、Next.js、Webpack、HTML、UniApp、Expo 和 Flutter 节点；检查阶段有 Web 交互、图表渲染、Dart Analyze 和 Flutter Build。

Knowledge 也按 ID 动态注册，避免把所有技术栈知识一次性塞入上下文。

### Q19：新增技术栈或检查器要改哪里？

推荐回答：

新增技术栈通常需要补充技术栈类型、启动或构建节点、专属 Knowledge，以及对应测试节点。新增检查器需要实现 `BaseNode`，输出标准结果；如果参与总分，还要写入 `extra.checkSignal`，然后注册并加入产线配置。

如果只是新增同协议模型，应主要修改模型适配层，不应扩散到 Pipeline。

### Q20：配置驱动有什么风险？

推荐回答：

风险包括节点 ID 拼错、参数缺失、节点顺序错误、依赖节点未配置，以及多个节点覆盖同一状态。当前实现能检查未知节点和部分核心参数，但节点间依赖仍有较多运行时校验。

演进方向是给每个节点增加参数 Schema、依赖声明、启动前拓扑预检和配置版本管理。

## 四、Agent 与执行纠偏

### Q21：需求扩写为什么重要？

推荐回答：

批量输入往往只有场景或短句，直接生成容易导致功能范围、平台和交互不明确。`detailed_prompt` 会按普通 Web、数据可视化或交互动效策略补充页面、视觉和交互要求，再由 `add_tech_stack` 追加工程约束。

风险是扩写偏离原意，因此应保留原始需求、版本化 Prompt，并用固定任务集比较扩写前后的需求一致性。

### Q22：Knowledge 如何注入？如何控制上下文？

推荐回答：

Knowledge 通过配置中的 ID 注册，框架只加载本次任务需要的知识，例如 Vite、Next.js、Flutter、图表或交互模式。这样比注入整个知识库更节省上下文。

长仓库场景还通过 `explore_repo` 让模型搜索和按需读取关键文件，但当前仍需要继续治理文件裁剪、摘要和缓存。

### Q23：工具拦截具体做什么？

推荐回答：

`beforeToolCall` 可以在真实工具执行前识别特殊工具。例如 `intercept_run_playwright_test` 会接管 Playwright 工具调用，统一生成或执行测试并写入质量信号；监控节点记录工具起止时间。

这个阶段也适合做命令权限、参数修正和危险操作拦截。

### Q24：Lint/Format 修复是模型做还是程序做？

推荐回答：

两种方式结合。TypeScript/JavaScript 写文件后先使用代码检查器发现问题；未使用变量等确定性问题可以程序化清理，其他问题则让本轮模型输出失效并重新生成。Dart 文件则直接执行 `dart fix --apply` 和 `dart format`。

原则是确定性问题交给工具，语义问题再交给模型。

### Q25：`style_fix` 和 `query_add` 有什么区别？

推荐回答：

`style_fix` 面向多轮样式修改，会生成递进任务、保存提交点、执行检查，失败时回滚到上一提交并继续修复。`query_add` 根据仓库、最近轨迹和代码修改记录生成一条新的功能或缺陷需求，控制最大追加次数后继续 Agent 循环。

一个偏样式迭代和回滚，一个偏功能扩展或缺陷续写。

### Q26：模型已经 `finish`，为什么还要二次修复？

推荐回答：

`finish` 只说明模型主观认为任务完成，它没有天然证明应用可运行、样式正确或需求覆盖完整。`afterTraceEnd` 是模型完成和平台验收之间的闸门，可以把后验发现的问题转成下一轮输入。

这使系统从单次生成变成可控的迭代过程。

### Q27：如何处理模型不调用工具、格式错误或调用过多工具？

推荐回答：

模型层根据 NFC、XML 或 JSON 解析工具调用。解析失败、无工具、JSON 非法、工具数量超限、`finish` 与其他工具混用时，会加入明确提示并重试。成功解析后会重置模型调用重试预算。

当前实现仍有递归重试分支，部分分支的预算递减不够统一，这是需要收敛为显式循环和统一预算的技术债。

### Q28：如何防止模型无限循环或无关修改？

推荐回答：

主循环通过 `maxLoop` 限制有效工具反馈轮次，模型调用还有重试预算；工具和仓库操作被限制在沙箱中。Prompt 也要求模型先读取仓库并完成验证。

但当前缺少统一的重复动作检测，例如连续读取同一文件或重复执行同一失败命令。更完善的方案应同时限制总耗时、Token、工具次数和重复调用次数。

## 五、自动测试与质量闭环

### Q29：Playwright 测试如何生成？

推荐回答：

一条链路先根据需求和代码轨迹生成结构化 checklist，再通过 `explore_repo` 搜索和读取真实仓库文件。随后以单个 checklist item 为粒度生成 Playwright 脚本，进行 Lint 校验，合并有效脚本，写入沙箱后启动真实服务并执行测试。

测试报告被解析为通过率、失败用例和 `checkSignal`。

### Q30：为什么按 checklist item 拆分生成？

推荐回答：

一次生成全部脚本容易遗漏步骤、输出截断，也难定位失败。按 item 拆分后，每次上下文更聚焦，单项可以独立进行最多 3 次 Lint 重试，并保留 `perItemReports`。

代价是模型调用成本增加，而且当前实现是串行生成，后续可以在资源预算内并行无依赖 item。

### Q31：为什么每个 step 对应一个 `test`？

推荐回答：

checklist 的评分粒度是 step。如果多个步骤合并为一个测试，只能得到整段结果，需求覆盖和失败定位都会变粗。代码要求每个 step 对应独立 `test`，名称包含 checklist ID 和 step 序号。

同一 item 使用 `describe.serial` 和共享 Page 保留业务状态，不同 item 彼此独立。

### Q32：如何约束测试使用真实 DOM？

推荐回答：

生成测试前通过 `explore_repo` 获取真实文件内容，并在 Prompt 中声明代码是选择器的唯一可信来源，优先使用真实 ID、`data-testid`、class 和文本。

这是一种上下文和 Prompt 约束，不是百分之百的静态保证。更强的方案是从 AST 或运行页面提取候选元素，再结构化校验脚本中的 locator。

### Q33：Lint 重试解决什么问题？

推荐回答：

它解决生成脚本中的语法错误、非法引用和部分静态问题。每个 checklist item 最多生成 3 次，只有通过 Lint 的脚本才进入合并，并记录尝试次数和最后错误。

Lint 只能证明脚本结构基本合法，不能证明选择器存在或断言正确，后面仍要真实执行。

### Q34：测试失败如何反馈给 Agent？

推荐回答：

通用 Agent 工具链可以通过 `run_playwright_test` 把执行结果作为工具结果回填模型，使模型根据失败继续修改。checklist 专项节点则进行“整批生成 -> 执行 -> 读取 rate”的最多 3 轮重生成。

当前 checklist 节点主要重新生成测试脚本，不等同于自动修复业务代码。面试时要区分“测试生成自修复”和“业务 Agent 依据测试结果修复”。

### Q35：“生成 -> 验证 -> 修复 -> 复测”如何运行？

推荐回答：

Agent 先完成代码生成；平台启动服务并执行检查；测试结果通过工具反馈或后置节点进入下一轮；模型修改后再次启动和验证。对于样式链路，`style_fix` 还会记录 Git 提交点，失败后回滚再试。

闭环的关键是失败证据要结构化，而不是只返回“测试失败”。

### Q36：自动生成测试是否存在自证正确？

推荐回答：

存在。模型可能根据错误实现生成弱测试，也可能遗漏需求。当前通过原始需求 checklist、真实仓库上下文、静态检查、真实浏览器执行、Rubrics、独立验证 Agent 和人工抽检降低风险。

但生成测试不能作为唯一真值。关键 benchmark 应维护人工黄金测试，并尽量让代码生成模型与评测模型隔离。

### Q37：如何识别弱断言？

推荐回答：

当前 Prompt 明确要求每个 step 至少一个有意义的 `expect`，禁止 `if` 条件断言和只依赖臆造选择器。Rubrics 和独立验证节点也能从轨迹或结果侧补充判断。

当前代码中还没有完整的 AST 弱断言检测器，这是明确的优化空间，可以检查无意义常量断言、条件包裹断言、缺少状态变化和只验证页面存在等模式。

### Q38：E2E、静态分析、构建和视觉评估如何取舍？

推荐回答：

它们验证不同维度：

- 构建和静态分析验证工程可用性；
- E2E 验证核心功能；
- 图表或点击检查验证专项交互；
- 视觉评估验证布局、美观和参考图还原；
- Rubrics 和轨迹评估验证过程质量。

核心功能场景应以构建和 E2E 为门禁，视觉和轨迹评分作为分项，不能互相抵消。

## 六、批量质量与稳定性

### Q39：`checkSignal` 是什么？有哪些来源？

推荐回答：

`checkSignal` 是统一的质量信号数组，每项包含节点 ID 和数值分数。当前可由 Playwright、Flutter Test、Dart Analyze、Flutter Build、样式检查、点击检查、图表渲染和 Rubrics 等节点写入。

部分节点只把结果写入 `extra`，例如 `agent_verify` 和 `trajectory_judge` 当前并未直接进入 `checkSignal`。

### Q40：`pass_rate` 如何计算？

推荐回答：

当前 `computeSignal` 会把所有 `checkSignal.signal` 相加后除以数量，也就是简单算术平均。

优点是统一、实现简单；缺点是默认各检查器同等重要，而且 `-1`、构建失败和视觉分之间的语义并不一致。更合理的方案是门禁项加场景权重，并保留分项结果。

### Q41：构建失败、功能失败和视觉失败权重一样吗？

推荐回答：

业务上不应该一样，但当前总分实现是简单平均。我的改进建议是：

- 构建失败或核心 E2E 失败直接判无效；
- 功能、视觉和轨迹按场景配置权重；
- 外部服务不可用单独标记 `unknown/degraded`，不直接当作代码低质量；
- 总分之外必须保留分项和证据。

### Q42：批量合成最容易失败在哪里？

推荐回答：

常见失败点包括模型工具格式、仓库克隆与依赖安装、服务启动、生成测试语法或选择器、浏览器环境、外部评测提交与轮询。

排障时应按“模型生成、工具协议、沙箱环境、应用代码、测试脚本、外部依赖”分类，而不是只看最终 `failed`。

### Q43：外部 SDK 波动怎么处理？

推荐回答：

对幂等的沙箱命令、文件写入、上传和外部请求使用有限次数重试，并设置单次超时；异步评测采用任务 ID 轮询并设置总截止时间。最终失败时保留节点、错误、耗时和降级状态。

不能对业务错误无差别重试，也不能吞掉错误伪装成功。

### Q44：如何避免无限重试？

推荐回答：

正确做法是同时设置单操作次数、阶段次数、Agent 最大轮次、任务总耗时和成本预算。当前部分节点已有 3 次或 5 次限制，Agent 有 `maxLoop` 和调用重试字段。

但引擎的 `retry` 会递归重新执行阶段，且部分模型重试分支预算不统一。长期应改成显式状态机，统一维护任务级重试预算。

### Q45：什么错误可以降级，什么必须阻断？

推荐回答：

构建失败、服务无法启动、核心测试无法执行、仓库状态损坏应阻断。辅助报告上传、截图保存或非核心外部评分可以降级，但必须在结果中保留失败状态。

`skipError=true` 的正确含义是“非阻断失败继续执行”，不是“这一步成功”。

### Q46：如何做错误分类和定位？

推荐回答：

每个节点应记录阶段、节点 ID、参数摘要、错误类型、耗时、重试次数和最终状态。模型调用和工具调用分别监控，测试阶段保留脚本、命令输出、失败标题、报告和截图。

这些信息可以把问题归类为生成错误、协议错误、环境错误、应用错误、测试错误或外部依赖错误。

### Q47：看哪些指标判断产线质量？

推荐回答：

我会看：

- 有效样本率；
- 服务启动和构建通过率；
- 核心功能测试通过率；
- checklist step 覆盖率；
- 首次通过率与重试恢复率；
- 弱断言率和人工抽检一致性；
- 各节点失败分布；
- 单样本模型调用次数、Token 和成本；
- 端到端 P95 耗时；
- 不同模型、技术栈和批次的质量方差。

只看最终 `pass_rate` 容易掩盖测试变弱或外部服务异常。

### Q48：如何提升有效样本率？

推荐回答：

优先级应是：

```text
提升 Prompt 和 Knowledge 的任务理解
-> 提升沙箱、依赖和服务启动稳定性
-> 加强 Checker 与测试反馈
-> 使用 afterTraceEnd 做针对性二次修复
-> 优化评分门禁和样本筛选
-> 最后优化并发、缓存和单位成本
```

先修复高频、可恢复的系统失败，再优化模型能力，避免把环境问题误判为模型问题。

## 七、最危险的追问

### Q49：你说“重点负责”，具体是哪几个节点？

推荐回答：

不要背整个节点列表。按真实参与情况选择 2-4 个最熟悉的节点，讲清输入、输出、失败分支和验证方式。建议重点准备：

- `gen_playwright_by_checklist`；
- `run_playwright_test`；
- `checklist_aesthetics` 或相关 SDK 稳定性治理；
- 输入、Lint 修复或监控节点中的实际参与部分。

### Q50：如何证明你的优化有效？

推荐回答：

没有正式统计时不报虚假百分比。我会固定同一批仓库、需求、模型版本和参数，对比改造前后的脚本 Lint 通过率、测试可执行率、有效样本率、首次通过率、重试恢复率、人工抽检一致性和 P95 耗时。

同时报告样本量和失败分布，避免只展示一个总体分数。

### Q51：当前实现最大的技术债是什么？

推荐回答：

我认为主要有四点：

1. `pass_rate` 简单平均，缺少阻断门禁和场景权重；
2. 部分重试采用递归且预算不统一；
3. 测试脚本合并使用文本规则，不如 AST 稳健；
4. 真实 DOM 和弱断言主要依赖 Prompt，结构化校验仍不足。

主动承认边界并给出演进路径，比把系统描述成完全成熟更可信。

## 八、三个 STAR 案例

### 案例一：Playwright checklist 自动评测闭环

- Situation：仓库级代码生成完成后缺少与需求步骤对应的功能验证。
- Task：建立从 checklist 到可执行 Playwright 脚本和评分结果的链路。
- Action：先探索真实仓库；按 checklist item 拆分生成；约束每个 step 对应独立测试；增加单项 Lint 重试；合并脚本并在沙箱执行；记录失败标题、通过率和质量信号。
- Result：形成“需求 -> 代码上下文 -> 测试 -> 执行 -> 评分”的可复用闭环。量化时使用脚本合法率、可执行率、step 覆盖率和人工一致性。

### 案例二：模型完成后的二次纠偏

- Situation：模型调用 `finish` 不代表样式、功能和工程质量已经通过平台验收。
- Task：在不破坏统一 Agent 主循环的前提下支持多轮修复。
- Action：利用 `afterTraceEnd` 挂载 `style_fix` 或 `query_add`；将新需求加入消息；样式场景保存 Git 提交点，失败时回滚；达到轮次后再进入正式检查。
- Result：把一次性生成升级为有边界的迭代修复，并保留每轮轨迹和仓库状态。

### 案例三：外部评测稳定性治理

- Situation：沙箱命令、文件写入、报告上传和外部评测轮询存在瞬时失败。
- Task：降低基础设施波动对批量任务的影响，同时避免静默吞错。
- Action：对幂等调用增加有限重试和超时；异步任务按 request ID 轮询；区分阻断失败与非阻断降级；记录节点状态、错误和耗时。
- Result：任务失败能够被分类和追踪，瞬时依赖异常具备恢复机会。正式效果以重试恢复率和外部依赖失败率衡量。

## 十、面试边界

- 不披露内部域名、接口、Token、部门数据或未公开模型名称。
- 不把 CommonFrameworkV1 整体描述成个人独立完成。
- 不说“真实 DOM 完全不会臆造”，当前主要是上下文和 Prompt 约束。
- 不说“所有失败都会自动修复”，不同节点的反馈方式和失败语义不同。
- 不用 `pass_rate` 单独证明质量，主动说明简单平均的局限。
- 不虚构有效样本率、成功率或成本下降比例。
